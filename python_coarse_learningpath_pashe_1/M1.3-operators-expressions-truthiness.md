# Phase 1 · M1.3: Operators, Expressions & Truthiness

## 1. Learning Objectives

- Use arithmetic, comparison, logical, bitwise, and identity operators correctly
- Understand operator precedence without needing to memorize the full table
- Explain Python's truthiness rules and use them idiomatically

## 2. Theory

Operators in Python are largely **syntactic sugar for dunder method calls** — `a + b` calls `a.__add__(b)` (falling back to `b.__radd__(a)`). This is _why_ operator overloading works uniformly across built-in and custom types (explored fully in Phase 2's data model module).

### Truthiness

Every object has an implicit boolean value via `__bool__` (or `__len__` as fallback). Falsy values: `None`, `False`, `0`, `0.0`, `""`, `[]`, `{}`, `set()`, empty containers generally. Everything else is truthy. This is _why_ `if my_list:` is idiomatic Python instead of `if len(my_list) > 0:` — it's not just shorter, it's the intended idiom, working uniformly across any type implementing `__bool__`/`__len__`.

### Short-circuit evaluation

`and`/`or` don't return `True`/`False` — they return one of their **operands**. `a or b` returns `a` if truthy, else `b`. This underlies the common `value = user_input or "default"` idiom.

### Chained comparisons

`1 < x < 10` is NOT two independent comparisons combined — it's syntactic sugar evaluating `x` only once, equivalent to `1 < x and x < 10` but more efficient and readable.

## 3. Visual Explanation

```bash
a + b     →  a.__add__(b)  (falls back to b.__radd__(a) if NotImplemented)
if obj:   →  bool(obj)     →  obj.__bool__() or len(obj) != 0
a or b    →  a if bool(a) else b     (returns an operand, not a bool)
```

## 4. Real-World Example

`config.get("timeout") or 30` is a common (but subtly risky) production pattern — if `timeout` is explicitly set to `0` (a valid "no timeout" value), `or` will incorrectly substitute `30` because `0` is falsy. The correct idiom is `config.get("timeout", 30)` or an explicit `is None` check — a real bug class that trips up even experienced engineers.

## 5. Best Practices

- Use truthiness idiomatically for emptiness checks (`if items:` not `if len(items) > 0:`)
- Be deliberate about `or`-as-default vs explicit `is None` checks when `0`/`""`/`False` are valid values
- Use chained comparisons for range checks instead of `and`

## 6. Common Mistakes

- The `x or default` trap when falsy-but-valid values exist (shown above)
- Confusing `is` (identity) with `==` (equality) in comparisons
- Overusing bitwise operators (`&`, `|`) where logical (`and`, `or`) was intended, or vice versa — especially in pandas/NumPy boolean masking contexts, where bitwise is actually required

## 7. Performance Considerations

Short-circuit evaluation is a performance feature, not just a convenience — `expensive_check() and cheap_check()` ordering matters; put cheap/likely-to-fail checks first.

## 8. Security Considerations

Falsy-value bugs (`or`-as-default) in security-relevant config (e.g., a `strict_mode or default_permissive` pattern) can silently disable security controls when a valid falsy value is intended — treat this pattern with extra scrutiny in security-sensitive code paths.
