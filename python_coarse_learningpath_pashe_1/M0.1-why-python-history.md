# Phase 0 · M0.1: Why Python? History & Implementations

## 1. Learning Objectives

- Explain Python's design philosophy and why it looks/behaves the way it does
- Name the major Python implementations and when you'd choose each
- Read and internalize the Zen of Python (PEP 20) as a design lens for later decisions

## 2. Theory

Python was created by **Guido van Rossum**, released in **1991**, as a successor to the ABC language, aiming to be more readable and general-purpose. Key milestones: Python 2.0 (2000, added list comprehensions, GC), Python 3.0 (2008, breaking change — unified str/unicode, print as function, true division), the long 2→3 migration (ending official Py2 support in 2020), and the ongoing performance push (3.11 "faster CPython" project, 3.13 free-threaded/no-GIL experimental build).

**Design philosophy (PEP 20, "Zen of Python")**: readability counts, explicit is better than implicit, simple is better than complex, there should be one obvious way to do it. This isn't just poetry — it's why Python favors clear keyword-based APIs over terse operator-heavy syntax (contrast with Perl, from which Python deliberately differentiated).

**Implementations** (Python is a *language spec*; CPython is just the reference implementation):

- **CPython** — the standard, C-based, reference implementation. What "Python" means by default.
- **PyPy** — JIT-compiled, often 4-10x faster for long-running pure-Python code; weaker C-extension compatibility.
- **Jython** — runs on the JVM, interoperates with Java (largely dormant now).
- **IronPython** — .NET interop (niche today).
- **MicroPython/CircuitPython** — for microcontrollers/embedded systems.
- **GraalPy** — runs on GraalVM, polyglot interop, newer entrant.

### WHEN to use which

- Default: CPython (best library support, what production tooling assumes)
- Long-running CPU-bound pure-Python service, no C-extension dependence: consider PyPy
- Embedded hardware: MicroPython
- Deep Java interop: Jython (rare today)

### Trade-offs

CPython's simplicity and C-API stability are why the entire scientific/ML ecosystem (NumPy, pandas, PyTorch) is built on it — but that same C-API is part of why the GIL has been so hard to remove (covered in Phase 3).

## 4. Real-World Example

Instagram (one of the largest Python deployments in the world) runs on CPython at massive scale, investing heavily in the "faster CPython" effort with Meta engineers — proof that implementation choice + optimization investment matters more than switching languages for many web-scale problems.

## 5. Best Practices

- Default to CPython unless you have a specific, measured reason not to
- Read PEP 20 once, then periodically — it explains *why* idiomatic Python looks the way it does
- Track Python's release cadence (annual, October releases) and EOL schedule for production planning

## 6. Common Mistakes

- Assuming "Python is slow" as a language property rather than an implementation/GIL property
- Picking PyPy without checking C-extension dependency compatibility first
- Ignoring Python EOL dates in production planning (each version supported ~5 years)

## 7. Performance Considerations

CPython performance has meaningfully improved since 3.11 (Cinder-derived optimizations, adaptive specializing interpreter, PEP 659) — "Python is slow" is increasingly outdated as a blanket claim; benchmark on your actual version.

## 8. Security Considerations

Old, unsupported Python versions (e.g., Python 2, EOL'd 3.x) stop receiving security patches — a governance/process issue as much as a technical one; production systems must track EOL dates.
