# Phase 1 · M1.11: Modules, Packages & the Import System

## 1. Learning Objectives

- Explain what happens when Python executes an `import` statement
- Structure a multi-file project into packages correctly
- Use relative vs absolute imports appropriately

## 2. Theory

### What `import` actually does

`import foo` triggers CPython's import machinery: it checks `sys.modules` (a cache — a module is only ever executed **once** per process, on first import; subsequent imports just fetch the cached module object), then searches `sys.path` for a matching file/package, executes the module's top-level code exactly once, and binds the resulting module object into the current namespace. This is _why_ import side effects (e.g., a print statement at module level) only ever fire once, and _why_ mutable module-level state acts like a process-wide singleton.

### Packages and `__init__.py`

A directory becomes a **package** (importable as `import mypackage`) when it contains an `__init__.py` (or, since Python 3.3, via "namespace packages" without one — a more advanced, less common pattern). `__init__.py` can be empty, or can control what's exposed when the package is imported.

### Absolute vs relative imports

```python
# absolute (preferred, unambiguous)
from mypackage.utils import helper

# relative (only valid inside a package, based on current module's position)
from .utils import helper       # same package
from ..other import thing        # parent package
```

Absolute imports are generally preferred for clarity — relative imports can become confusing as a package grows, and only work correctly for modules being imported as part of a package (not run directly as a script), a frequent source of `ImportError: attempted relative import with no known parent package` confusion for beginners.

### `sys.path` and how Python finds modules

`sys.path` is a list of directories searched in order. It includes the script's directory, `PYTHONPATH` env var entries, and installed-package locations (`site-packages`). Understanding this explains most "ModuleNotFoundError" confusion — it's almost always a `sys.path`/working-directory/environment mismatch, not a "Python is broken" issue.

## 4. Real-World Example

A very common beginner-to-intermediate confusion: running `python mypackage/module_a.py` directly, where `module_a.py` contains `from . import module_b` — this fails with `ImportError`, because running a file directly doesn't give it "package context." The fix is either running via `python -m mypackage.module_a` (which does establish package context) or restructuring with an explicit entry-point script that imports the package properly.

## 5. Best Practices

- Prefer absolute imports for anything beyond very small packages
- Structure projects with a clear `src/` layout (`src/mypackage/...`) to avoid accidental imports of the working directory instead of the installed package — a subtle, common packaging bug
- Avoid import-time side effects beyond simple definitions (no network calls, no heavy computation at module level)

## 6. Common Mistakes

- `ImportError: attempted relative import with no known parent package` from running a package module as a script directly
- Circular imports (module A imports module B which imports module A) — usually a sign of a design/architecture issue, not just an import-order issue
- Shadowing stdlib module names with your own files (e.g., naming a file `json.py` in your project root, breaking `import json` for the real standard library)

## 7. Performance Considerations

Because modules execute once and are cached, expensive setup (e.g., loading a large ML model) is often deliberately placed at module level specifically to amortize the cost across the process's lifetime — a legitimate, common pattern, distinct from the "avoid import side effects" guidance above (the distinction: intentional, well-understood initialization vs accidental/hidden side effects).

## 8. Security Considerations

Python's import search order means a malicious file matching a stdlib or dependency module's name, placed earlier in `sys.path` (e.g., in the current working directory), can shadow and hijack imports — a real supply-chain attack vector; the `src/` layout and careful `sys.path`/working-directory hygiene mitigate this.
