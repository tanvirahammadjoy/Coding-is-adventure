# Phase 1 · M1.10: File I/O, Context Managers & pathlib

## 1. Learning Objectives

- Read/write text and binary files correctly and safely
- Use context managers (`with`) idiomatically for resource management
- Prefer `pathlib` over string-based `os.path` manipulation

## 2. Theory

### Why `with open(...) as f:` exists

A file handle is an OS resource that must be explicitly released (closed) — failing to close files can exhaust OS file-descriptor limits in long-running processes, a real production failure mode. `with` guarantees `f.close()` runs even if an exception occurs inside the block, by using the **context manager protocol** (`__enter__`/`__exit__` — full mechanics in M2.8). This is _why_ `with` is considered mandatory best practice, not a style preference.

### Text vs binary mode

`open(path, "r")` (text mode, default) decodes bytes to `str` using a specified/inferred encoding. `open(path, "rb")` (binary mode) returns raw `bytes`, no decoding — required for non-text files (images, binary protocols) and sometimes for text files where you need full control over encoding/newline handling.

### pathlib vs os.path

`pathlib.Path` (stdlib since 3.4) represents filesystem paths as **objects** with methods (`.exists()`, `.read_text()`, `/` operator for joining) rather than strings passed to free functions (`os.path.join`, `os.path.exists`). This is _why_ pathlib is now preferred — it's more readable, less error-prone (no manual separator handling), and cross-platform by construction.

```python
from pathlib import Path
p = Path("data") / "input.csv"     # cross-platform join via /
if p.exists():
    text = p.read_text(encoding="utf-8")
```

## 3. Visual Explanation

```python
with open(path) as f:      →  f = open(path); f.__enter__()
    data = f.read()                    ... block body ...
                            →  f.__exit__()  →  f.close()  (guaranteed, even on exception)
```

## 4. Real-World Example

A long-running data-processing service that opened files without `with` (relying on garbage collection to eventually close them) hit `OSError: Too many open files` under load — a classic resource-leak incident, fixed simply by ensuring every `open()` call used a `with` block or was wrapped in a context manager.

## 5. Best Practices

- Always use `with open(...) as f:` — never bare `open()`/`close()` pairs
- Use `pathlib.Path` for all new path manipulation code
- Always specify `encoding="utf-8"` explicitly for text files (platform default encoding varies and is a common cross-platform bug source)

## 6. Common Mistakes

- Forgetting to close files (file-descriptor leaks in long-running processes)
- Mixing text and binary mode incorrectly, causing `TypeError` or garbled data
- Relying on the platform default encoding instead of specifying one explicitly

## 7. Performance Considerations

For large files, avoid `f.read()` (loads entire file into memory) — iterate line-by-line (`for line in f:`) or read in fixed-size chunks for binary data, keeping memory usage bounded regardless of file size (echoing M1.8's generator-expression memory lesson).

## 8. Security Considerations

Never construct file paths by concatenating untrusted user input directly (**path traversal** vulnerability, e.g., a filename like `"../../etc/passwd"`) — validate/sanitize paths, and use `Path.resolve()` combined with checking the result stays within an expected base directory.
