# Phase 0 · M0.6: PEP 8, PEP 257, Linters & Formatters

## 1. Learning Objectives

- Apply PEP 8 style conventions and PEP 257 docstring conventions
- Set up automated linting/formatting/type-checking in a project
- Understand the modern (2025/2026) tooling consolidation around `ruff`

## 2. Theory

**PEP 8** is Python's style guide (naming, whitespace, line length, import ordering). **PEP 257** covers docstring conventions. Neither is enforced by the interpreter — they're _community_ standards, enforced by tooling.

### The tool landscape

- **flake8** — classic linter, plugin-based, checks style + some bugs
- **black** — "uncompromising" auto-formatter, near-zero configuration, ends style debates by removing choice
- **isort** — import sorting
- **mypy** — static type checker (uses `typing` annotations)
- **pyright** — Microsoft's type checker (also powers Pylance), often faster than mypy
- **ruff** — Rust-based, extremely fast, has increasingly **replaced flake8 + isort + parts of black's role** as a near-all-in-one linter/formatter as of 2024–2026, due to 10-100x speed and low-config ergonomics

### WHY automated formatting exists

Human style debates in code review waste time and create friction without improving correctness. Deterministic formatters remove the debate entirely — diffs stay minimal, and reviewers focus on logic, not spacing.

### WHEN NOT to over-lint

Aggressive linting on legacy/inherited codebases can generate thousands of warnings that drown signal — introduce incrementally (lint only changed lines, or fix module-by-module) rather than a "big bang" pass that blocks all other work.

## 3. Visual Explanation

```bash
source.py → ruff (lint + format) → mypy/pyright (types) → pytest (tests) → commit
             ↑ pre-commit hook runs this automatically before every commit
```

## 4. Real-World Example

Most modern Python OSS projects (FastAPI, many Django-ecosystem packages) have migrated their CI and pre-commit configs from flake8+black+isort to ruff alone, cutting lint/format CI step time from tens of seconds to under a second — a small but compounding cost saving at CI scale (ties to M5.9).

## 5. Best Practices

- Automate formatting via pre-commit hooks, not manual discipline
- Keep a single source of truth config (`pyproject.toml`) for all tools
- Treat type-checker warnings as seriously as test failures in CI for any codebase using type hints

## 6. Common Mistakes

- Configuring conflicting rules between tools (e.g., black and a linter disagreeing on line length)
- Adding strict linting to a legacy codebase all at once, blocking unrelated PRs with thousands of pre-existing violations
- Ignoring docstring conventions, making auto-generated documentation (Sphinx) unusable later

## 7. Performance Considerations

Rust-based tooling (ruff, uv) has meaningfully changed Python's developer-experience performance profile — CI lint/format steps that took 10-30s with flake8+black often complete in under 1s with ruff, compounding across thousands of CI runs.

## 8. Security Considerations

Some linter plugins can flag known-insecure patterns (e.g., `bandit`, or ruff's security-rule subset) — hardcoded secrets, use of `eval`, weak crypto calls — integrate these into CI as an early security net, not a replacement for real security review (Phase 4).

## 9. Hands-On Exercises

1. Install ruff, run it against a messy sample script, and fix all reported issues
2. Set up a pre-commit hook that runs ruff automatically before every commit
3. Add type hints to a small function and run mypy or pyright against it

## 10. Mini Project

Take any script from Phase 1 exercises, add a full `pyproject.toml` with ruff + mypy config, get it to a completely clean lint/type-check pass, and write a short README documenting the setup for a new contributor.

## 11. Interview Questions

- Junior: "What's the difference between a linter and a formatter?"
- Mid: "How would you introduce strict linting into a large legacy codebase without blocking the team?"
- Senior: "Design a pre-commit + CI pipeline strategy for a 40-person engineering org with mixed codebase maturity."

## 12. Challenge Exercise

Configure ruff to replicate (as closely as possible) a flake8+black+isort setup, document any behavioral differences you find, and decide whether they matter for a real team.
