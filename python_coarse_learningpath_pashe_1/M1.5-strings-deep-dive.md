# Phase 1 · M1.5: Strings Deep Dive — Immutability, Unicode & Formatting

## 1. Learning Objectives

- Explain why Python strings are immutable and what that implies for performance
- Understand Python 3's Unicode-by-default string model and UTF-8 encoding/decoding
- Choose the right string formatting approach for a given situation

## 2. Theory

Python `str` is **immutable** — every "modification" (`.upper()`, concatenation, `.replace()`) creates a **new** string object. This is _why_ string concatenation in a loop (`s += chunk`) is O(n²) in naive form — each `+=` allocates a new, larger string and copies everything.

### Unicode by default (Python 3's biggest break from Python 2)

Python 3 `str` is a sequence of **Unicode code points**, not bytes. Encoding (`str.encode()`) converts to `bytes` (e.g., UTF-8); decoding (`bytes.decode()`) does the reverse. This is _why_ Python 2's implicit str/unicode mixing (a major source of bugs, especially with non-ASCII text) was fixed at the cost of a painful, decade-long ecosystem migration (2008–2020).

### Formatting approaches

- **f-strings** (3.6+) — fastest, most readable, evaluated at runtime, preferred default
- **`.format()`** — more verbose, useful when the template is data (not known until runtime, e.g., loaded from a config file)
- **`%` formatting** — legacy, still seen in `logging` calls (deliberately, for lazy evaluation — see Performance below) and old codebases

## 3. Visual Explanation

```python
"hello" + " " + "world"   →  creates 3 intermediate strings, then discards them (immutability)
str.encode('utf-8')  →  bytes
bytes.decode('utf-8') →  str
```

## 4. Real-World Example

A classic production bug: reading a file assuming UTF-8 when it's actually Latin-1 (common with legacy Windows-generated CSVs) raises a `UnicodeDecodeError` — or worse, silently produces mojibake if decoded with `errors='replace'` carelessly. Explicitly specifying and validating encoding at I/O boundaries prevents an entire class of "weird characters in prod" bugs.

## 5. Best Practices

- Use f-strings by default for readability and performance
- Use `logging.info("value=%s", x)` (lazy `%`-style) in logging calls specifically, so string formatting is skipped entirely when the log level is disabled — a real performance detail, not just style
- Use `"".join(chunks)` instead of `+=` in a loop for building large strings
- Always be explicit about encoding at I/O boundaries (`open(path, encoding="utf-8")`)

## 6. Common Mistakes

- `s += chunk` in a loop for large strings (O(n²) — use `"".join()`)
- Assuming file encoding without specifying it explicitly
- Using f-strings inside logging calls (`logging.info(f"value={x}")`) — this defeats lazy evaluation, formatting the string even when the log level would discard it

## 7. Performance Considerations

CPython does have some optimizations mitigating naive `+=` cost in specific cases (string interning, in-place resize when refcount is 1), but this is a CPython implementation detail you should **never rely on** — `"".join()` is the portable, guaranteed-efficient idiom.

## 8. Security Considerations

Never build SQL/shell commands via string formatting/concatenation with untrusted input — this is the root cause of SQL injection and command injection (covered fully in Phase 4's security module); always use parameterized queries/subprocess argument lists instead.
