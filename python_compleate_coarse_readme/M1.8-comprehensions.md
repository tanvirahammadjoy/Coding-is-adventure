# Phase 1 · M1.8: Comprehensions — List, Dict, Set & Generator

## 1. Learning Objectives

- Write list/dict/set comprehensions and generator expressions fluently
- Know when a comprehension improves readability and when it hurts it
- Understand that comprehensions have their own local scope (Python 3 behavior)

## 2. Theory

A comprehension is a compact expression for building a collection from an iterable, optionally filtered:

```python
squares = [x**2 for x in range(10)]                 # list
evens_set = {x for x in range(10) if x % 2 == 0}      # set
lookup = {x: x**2 for x in range(10)}                 # dict
lazy = (x**2 for x in range(10))                      # generator expression (lazy!)
```

### WHY they exist

They express the extremely common "transform + filter" pattern more concisely and (often) faster than an equivalent manual loop with `.append()`, because the loop internals are implemented in optimized C-level bytecode specific to comprehensions, avoiding repeated attribute lookups (`.append`) on every iteration.

### Own scope (Python 3 change from Python 2)

Comprehensions have their **own local scope** since Python 3 — the loop variable does not leak into the enclosing scope (unlike Python 2, and unlike a plain `for` loop in Python 3, which _does_ leak its variable). This is a deliberate correctness fix.

### WHEN NOT to use a comprehension

When the transform logic requires multiple statements, side effects, or exception handling per item — a comprehension packed with a hidden function call or complex conditional expression to force it into one line is a **readability regression**, not an improvement. A plain loop is more Pythonic in that case.

## 3. Visual Explanation

```bash
[expr for item in iterable if condition]
  ↑        ↑            ↑           ↑
result   what to    where from   optional filter
         produce
```

## 4. Real-World Example

Data-cleaning pipelines commonly overuse nested comprehensions (`[f(x) for row in data for x in row if cond(x)]`) to the point of unreadability — a senior engineer reviewing such code typically requests it be unpacked into a named function + a simple loop or a `filter`/`map` chain, trading a few lines for maintainability.

## 5. Best Practices

- Keep comprehensions to one, at most two, logical clauses of complexity
- Use a generator expression (not a list comprehension) when you don't need the whole collection materialized in memory at once (e.g., feeding into `sum()`, `any()`, `all()`)
- Extract complex per-item logic into a named helper function, then call it inside a simple comprehension

## 6. Common Mistakes

- Nested comprehensions that sacrifice readability for compactness
- Materializing a huge list with a list comprehension when a generator expression would avoid the memory cost
- Using a comprehension purely for side effects (e.g., `[print(x) for x in items]`) — this is not idiomatic; use a plain loop for side effects

## 7. Performance Considerations

List comprehensions are typically faster than an equivalent manual loop with `.append()` due to specialized bytecode — but generator expressions trade a small per-item overhead for **constant memory usage**, which matters enormously for large/streaming datasets (a list comprehension over a billion-row file will exhaust memory; a generator won't).

## 8. Security Considerations

Comprehensions processing untrusted external data (e.g., building SQL fragments or file paths per item) carry the same injection risks as any other per-item transform — the compact syntax doesn't reduce the need for validation/sanitization.

2. Rewrite a list comprehension processing a huge range as a generator expression, and demonstrate the memory difference conceptually (or with `sys.getsizeof`)
3. Identify and refactor an overly-nested comprehension into a readable loop + helper function
