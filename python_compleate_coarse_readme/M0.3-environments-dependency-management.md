# Phase 0 · M0.3: Environments & Dependency Management

## 1. Learning Objectives

- Explain why virtual environments exist and what problem they solve
- Compare venv, virtualenv, pipx, Poetry, PDM, uv, and Conda
- Choose the right tool for a given project type

## 2. Theory

A **virtual environment** is an isolated directory containing its own Python interpreter (symlinked) and `site-packages`, so each project's dependencies don't collide with another's or with the system.

### WHY this exists

Two projects on the same machine may need incompatible versions of the same library (e.g., `requests==2.20` vs `requests==2.31`). Without isolation, only one can be installed globally at a time.

### The tool landscape (2025/2026 state)

- **venv** (stdlib) — built-in, minimal, no dependency resolution beyond pip's
- **virtualenv** — predates venv, faster creation, slightly more features, still widely used
- **pipx** — installs and runs Python _applications_ (CLIs) in isolated environments, not for library dependency management
- **Poetry** — dependency resolution + packaging + virtualenv management in one tool, `pyproject.toml`-based, lockfile (`poetry.lock`)
- **PDM** — similar to Poetry, PEP 582/621 aligned, faster resolver
- **uv** (Astral) — extremely fast (Rust-based) drop-in replacement for pip/venv/pip-tools, rapidly becoming the modern default as of 2025/2026 for speed-sensitive workflows
- **Conda** — manages Python _and_ non-Python binary dependencies (critical for scientific computing with complex native deps like CUDA); heavier, separate package index

### WHEN to use which

- Simple scripts/learning: venv + pip
- Publishing a library or app with reproducible builds: Poetry or PDM
- Speed-critical CI, large monorepos: uv
- Data science/ML with heavy native dependencies (CUDA, MKL): Conda
- Installing CLI tools (e.g., `black`, `httpie`) system-wide without polluting envs: pipx

### Trade-offs

Poetry/PDM add resolver overhead and a learning curve but give reproducible lockfiles; raw venv+pip is simplest but has no lockfile by default (mitigated with `pip freeze` or `pip-tools`).

## 3. Visual Explanation

```bash
project/
├── .venv/            <- isolated interpreter + site-packages
├── pyproject.toml     <- declared dependencies
├── poetry.lock         <- exact resolved versions (reproducibility)
└── src/
```

## 4. Real-World Example

A company migrating a large monorepo's CI from pip+venv to `uv` reported dependency install times dropping from minutes to seconds — meaningful at the scale of hundreds of CI runs/day, directly cutting cloud CI cost (ties into M5.9 cost optimization later).

## 5. Best Practices

- Always work inside a virtual environment, never install project deps globally
- Commit lockfiles (`poetry.lock`, `uv.lock`, etc.) for reproducible builds
- Separate dev dependencies (linters, test tools) from runtime dependencies

## 6. Common Mistakes

- Committing `.venv/` to version control (bloats repo; add to `.gitignore`)
- Not pinning versions, leading to "works on my machine" drift
- Mixing Conda and pip installs carelessly in the same environment (can corrupt dependency resolution)

## 7. Performance Considerations

Resolver speed matters at scale: pip's resolver historically was slower/less robust than Poetry/uv's; uv's Rust implementation offers order-of-magnitude install speed improvements, materially affecting CI pipeline duration.

## 8. Security Considerations

Lockfiles pin exact versions including transitive dependencies — critical for reproducing a known-good, audited dependency tree, and for tools like `pip-audit`/`safety` to scan accurately.
