# Phase 0 · M0.4: Editors, IDEs & Developer Workflow

## 1. Learning Objectives

- Set up a productive Python development environment
- Understand what language servers do and why they matter
- Establish a terminal-first workflow that transfers to remote/server environments

## 2. Theory

Modern Python tooling relies heavily on the **Language Server Protocol (LSP)** — a standard letting any editor get autocomplete, type-checking, and navigation by talking to a language server (e.g., Pylance/Pyright for Python) rather than each editor reimplementing analysis.

### Options

- **VS Code + Pylance** — most popular, free, fast Pyright-based type checking, huge extension ecosystem
- **PyCharm** — full IDE, strongest refactoring tools, integrated debugger/profiler, heavier
- **Jupyter/JupyterLab** — notebook-based, best for data exploration/ML, poor fit for production software engineering workflow
- **Neovim + LSP** — terminal-native, fast, steep learning curve, popular among engineers who work heavily over SSH

### WHY terminal fluency still matters

Production debugging often happens over SSH into a server or a container with no GUI — comfort with `python`, `pip`, `pytest`, `pdb` at a bare terminal is a non-negotiable professional skill, regardless of your daily-driver editor.

## 3. Visual Explanation

```bash
Editor (VS Code) ⇄ LSP ⇄ Pyright/Pylance (type-checks, autocomplete, go-to-def)
Editor            ⇄       Debugger (debugpy) ⇄ running Python process
```

## 4. Real-World Example

Engineering teams standardize on a shared `.vscode/settings.json` + `pyproject.toml` (with ruff/black/mypy config) checked into the repo, so every contributor's editor enforces the same formatting/linting automatically on save — removing style debates from code review entirely.

## 5. Best Practices

- Enable format-on-save with a deterministic formatter (black/ruff format)
- Enable a linter and type checker in-editor, not just in CI, for fast feedback
- Learn your debugger's breakpoint/step/inspect workflow rather than relying solely on `print`

## 6. Common Mistakes

- Relying only on `print()` debugging for anything beyond trivial scripts
- Not configuring the editor to use the project's virtual environment (leads to false "module not found" errors)
- Ignoring in-editor type/lint warnings until CI fails

## 7. Performance Considerations

Large monorepos can make language servers slow (indexing time); scoping the workspace and excluding generated/vendor directories keeps IDE responsiveness reasonable.

## 8. Security Considerations

Be cautious installing third-party editor extensions with broad file-system/network access; review permissions, especially for AI-assisted coding extensions that may transmit code externally.

## 9. Hands-On Exercises

1. Set up VS Code with Pylance, point it at a venv, and confirm autocomplete/type-checking work
2. Set a breakpoint and step through a small script using the built-in debugger
3. Practice using `pdb` (`python -m pdb script.py`) from a raw terminal, no IDE

## 10. Mini Project

Configure a repo-level `pyproject.toml` with ruff + mypy + pytest config, and a `.vscode/settings.json` that makes VS Code respect all three automatically for any contributor who opens the folder.

## 11. Interview Questions

- Junior: "What is a language server and why does it matter?"
- Mid: "How do you debug a Python process running on a remote server with no GUI access?"
- Senior: "How would you standardize editor/tooling config across a team to reduce 'works on my machine' style debates?"

## 12. Challenge Exercise

Debug a deliberately broken script using only `pdb` at the terminal (no IDE) — practice `b` (breakpoint), `n`/`s` (step), `p` (print), `c` (continue), `l` (list) until you're comfortable navigating blind.
