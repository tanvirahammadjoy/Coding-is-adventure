# Phase 0 · M0.2: Installing Python Properly & Version Management

## 1. Learning Objectives

- Install Python without polluting/breaking the OS system Python
- Manage multiple Python versions side-by-side with pyenv
- Understand why "system Python" is dangerous to modify directly

## 2. Theory

Most operating systems (especially Linux, macOS) ship a **system Python** used internally by OS tools (package managers, scripts). Installing packages globally into it, or changing its version, can break the OS itself. This is *why* version managers exist.

**pyenv** works by shimming the `python` command: it installs isolated Python versions under `~/.pyenv/versions/`, and intercepts calls to `python`/`pip` to route to the version you've selected (globally, per-directory via `.python-version`, or per-shell).

### WHY this exists

Different projects need different Python versions (a legacy service on 3.9, a new service on 3.13). Without isolation, you're stuck on one version system-wide, or you manually manage PATH — brittle and error-prone.

### Alternatives

- **asdf** — generic multi-language version manager (Python is one plugin among many); good if you already manage other languages this way
- **Docker-based dev environments** — sidesteps host version management entirely by containerizing; heavier but maximally reproducible
- **Official python.org installers** — fine for a single-version simple setup, poor for multi-project multi-version work

### WHEN NOT to bother with a version manager

Simple learning/tutorial setup, single machine, single project — the official installer is fine to start Phase 1 with. Introduce pyenv once you have 2+ projects needing different versions (typically by Phase 2).

## 4. Real-World Example

A backend team maintaining a legacy service pinned to Python 3.8 (due to an unmaintained dependency) alongside new services on 3.12 uses a `.python-version` file per repo so `cd`-ing into each directory automatically switches versions — no manual PATH juggling, no CI mismatches.

## 5. Best Practices

- Never `sudo pip install` into system Python
- Commit a `.python-version` file to each repo for reproducibility
- Pin exact patch versions in CI to match production

## 6. Common Mistakes

- Installing packages globally with system pip, causing conflicts with OS tools (notably on Debian/Ubuntu, which now blocks this by default — PEP 668 "externally managed environment")
- Forgetting to reshim after installing a new version (`pyenv rehash`)
- Assuming `python` and `python3` point to the same install

## 7. Performance Considerations

Version manager overhead (shim indirection) is negligible at runtime — it only affects interpreter *selection*, not execution speed.

## 8. Security Considerations

Never disable OS package protections (e.g., forcing `pip install` into system Python with `--break-system-packages`) without understanding you may be introducing conflicting/vulnerable package versions into OS-critical scripts.

## 9. Hands-On Exercises

1. Install pyenv and two Python versions (e.g., 3.10 and 3.12)
2. Create two directories, each with a different `.python-version`, and verify `python --version` differs between them
3. Explain PEP 668 in your own words and demonstrate the error it prevents

## 10. Mini Project

Set up a "version matrix" test harness: a tiny script that runs a simple compatibility check (e.g., a piece of code using `match`/case, which requires 3.10+) against two pyenv-managed versions, and reports pass/fail per version.

## 11. Interview Questions

- Junior: "Why shouldn't you `pip install` directly into system Python?"
- Mid: "How does pyenv actually intercept the `python` command?"
- Senior: "How would you enforce consistent Python versions across developer machines and CI in a 50-engineer org?"
