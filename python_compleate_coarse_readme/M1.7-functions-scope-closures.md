# Phase 1 · M1.7: Functions — Arguments, Scope & Closures

## 1. Learning Objectives

- Use all argument types correctly (positional, keyword, default, `*args`, `**kwargs`)
- Explain Python's scoping rules (LEGB) precisely
- Understand what a closure is and why it "remembers" enclosing variables

## 2. Theory

### Argument types

```python
def f(a, b, /, c, d=10, *args, e, f=20, **kwargs): ...
```

- `a, b` before `/` — **positional-only** (PEP 570, 3.8+)
- `c, d` — positional-or-keyword
- `d=10` — default value (evaluated **once**, at def time — ties back to M1.1's mutable-default-argument bug)
- `*args` — extra positional args collected into a tuple
- `e, f` after `*args` — **keyword-only** arguments (must be passed by name)
- `**kwargs` — extra keyword args collected into a dict

### WHY positional-only and keyword-only exist

Positional-only (`/`) lets library authors change parameter _names_ in future versions without breaking callers who pass positionally (relevant for stdlib/API stability). Keyword-only (after `*`) forces callers to be explicit for arguments where positional use would be error-prone or unclear (e.g., `sorted(data, *, key=..., reverse=...)`).

### Scope — LEGB

Name resolution order: **L**ocal → **E**nclosing (closures) → **G**lobal (module) → **B**uilt-in. Python does NOT have block scope (unlike C/Java) — a variable assigned anywhere inside a function is local to that _entire function_, even before the assignment line (this is _why_ referencing a variable before its local assignment raises `UnboundLocalError` rather than falling back to a global of the same name).

### Closures

A closure is a function that **remembers** variables from an enclosing scope even after that scope has finished executing, by keeping a reference to those variables (via a `cell` object) rather than their value at definition time. This is _why_ the classic "closures in a loop" bug happens — all closures created in a loop share the _same_ cell, so they all see the loop variable's _final_ value, not the value at creation time.

```python
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]  # [2, 2, 2] — NOT [0, 1, 2]!
# Fix: capture i as a default argument
funcs = [lambda i=i: i for i in range(3)]  # [0, 1, 2]
```

## 3. Visual Explanation

```python
def outer():
    x = 10
    def inner():        # inner is a closure over x
        return x         # looked up via Enclosing scope (LEGB)
    return inner
```

## 4. Real-World Example

The closures-in-a-loop bug is extremely common when dynamically building callback handlers (e.g., registering multiple button handlers in a GUI, or route handlers in a lightweight web framework) in a loop — all handlers end up referencing the same final loop value unless explicitly captured via a default argument or `functools.partial`.

## 5. Best Practices

- Use keyword-only arguments for boolean flags and rarely-changed options to keep call sites self-documenting (`resize(img, width=800, *, keep_aspect=True)`)
- Capture loop variables explicitly in closures via a default argument or `functools.partial`
- Avoid mutable default arguments (M1.1); use `None` + create-inside-body instead

## 6. Common Mistakes

- The closures-in-a-loop bug
- `UnboundLocalError` from assigning to a variable inside a function that's also read before that assignment, expecting it to fall back to a global
- Overusing `**kwargs` to avoid defining a clear function signature, hurting readability/discoverability

## 7. Performance Considerations

Local variable access (fast array-slot lookup) is faster than global lookup (dict lookup) — a real (if usually minor) reason tight loops inside functions outperform equivalent module-level code, tying back to M1.1's LEGB performance note.

## 8. Security Considerations

`**kwargs`-heavy APIs that pass arguments through to something like a SQL query builder or shell command without validation are a common place for injection vulnerabilities to hide — explicit, typed signatures make security review far easier than opaque `**kwargs` passthrough.
