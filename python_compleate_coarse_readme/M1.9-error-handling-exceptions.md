# Phase 1 · M1.9: Error Handling & Exceptions

## 1. Learning Objectives

- Use try/except/else/finally correctly and understand each clause's purpose
- Understand Python's exception hierarchy and write appropriate custom exceptions
- Explain exception chaining (`raise ... from ...`) and why it matters for debugging

## 2. Theory

### The full try statement

```python
try:
    risky()
except SpecificError as e:
    handle(e)
except (TypeA, TypeB):
    handle_multiple()
else:
    only_if_no_exception()
finally:
    always_runs()
```

- `else` runs only if the `try` block succeeded — useful for code that should run on success but shouldn't itself be caught by the `except` clauses
- `finally` always runs — for cleanup (though context managers, M2.8, are usually the better tool for resource cleanup specifically)

### WHY exceptions exist (vs return-code error handling)

Exceptions separate the **error-handling path from the normal-logic path**, avoiding the C-style pattern of checking a return code after every single call. Python embraces **EAFP** ("Easier to Ask Forgiveness than Permission") over **LBYL** ("Look Before You Leap") as an idiom — e.g., `try: d[key] except KeyError:` is often preferred over `if key in d:` followed by access, partly for atomicity (avoiding race conditions between the check and the access) and partly as a style convention.

### Exception hierarchy

All exceptions inherit from `BaseException`. `Exception` is the base for "normal" errors you should generally catch; `BaseException` also includes `SystemExit`, `KeyboardInterrupt`, `GeneratorExit` — which you should almost never catch broadly (catching bare `except:` swallows Ctrl+C and system exit, a serious anti-pattern).

### Custom exceptions & chaining

```python
class InsufficientFundsError(Exception):
    def __init__(self, balance, requested):
        super().__init__(f"balance {balance} < requested {requested}")
        self.balance = balance
        self.requested = requested

try:
    withdraw(...)
except KeyError as e:
    raise InsufficientFundsError(...) from e   # preserves original traceback context
```

`raise ... from e` sets `__cause__`, producing a chained traceback ("The above exception was the direct cause of...") — critical for debugging in production, where losing the original root cause turns a 5-minute fix into an hour of guesswork.


## 4. Real-World Example

A production incident postmortem pattern: a bare `except:` (or `except Exception:` without re-raising/logging) silently swallowed a `KeyError` deep in a payment-processing pipeline, causing transactions to silently fail with no error surfaced — the fix was narrowing the except clause to the specific expected exception and ensuring all others propagate/log with full context.

## 5. Best Practices

- Catch the most **specific** exception type possible, never bare `except:`
- Always log or re-raise — never silently swallow an exception
- Use `raise ... from e` when translating one exception type to another
- Reserve custom exceptions for genuinely distinct error conditions callers need to handle differently

## 6. Common Mistakes

- Bare `except:` (catches `SystemExit`/`KeyboardInterrupt` too — can make a program un-killable via Ctrl+C in pathological cases)
- Catching `Exception` broadly "just in case" and silently passing, hiding real bugs
- Using exceptions for ordinary control flow where a simple conditional would be clearer
- Losing the original traceback by re-raising without `from e`

## 7. Performance Considerations

Exception handling in CPython is cheap when no exception is raised (the `try` block itself has near-zero overhead) but raising/catching an exception has real cost — avoid using exceptions for high-frequency expected control flow (e.g., using `StopIteration`-style exceptions per-item in a hot loop processing millions of items); reserve them for genuinely exceptional conditions.

## 8. Security Considerations

Never include sensitive data (passwords, tokens, full stack traces with internal paths) in exception messages surfaced to end users/API responses — log full detail internally, return generic messages externally, to avoid information disclosure.
