# Phase 1 · M1.6: Collections — list, tuple, set, dict Internals

## 1. Learning Objectives

- Choose the right built-in collection for a given access pattern
- Explain the internal implementation of each (dynamic array vs hash table)
- Reason about Big-O costs of common operations from first principles

## 2. Theory

### list — dynamic array

CPython's `list` is a resizable array of pointers (not a linked list). Appending is **amortized O(1)** (the underlying array over-allocates and grows geometrically, so most appends don't require a resize). Indexing (`lst[i]`) is O(1) — direct pointer arithmetic. **Inserting/deleting at the front or middle is O(n)** — every subsequent element must shift.

### tuple — immutable, fixed-size array

Same underlying array representation as list, but immutable and fixed-size at creation — enabling minor memory/performance advantages and, critically, **hashability** (tuples of hashable elements can be dict keys/set members; lists cannot).

### dict — hash table

CPython's `dict` (since 3.7, insertion order is guaranteed as a language spec, not just implementation detail) is a hash table: keys are hashed (`__hash__`) to determine bucket placement, giving **average O(1)** lookup/insert/delete. Hash collisions are resolved via open addressing. This is _why_ dict keys must be hashable (hence immutable, generally) — mutable objects can't safely be hashed since mutation would change their hash and break the table's internal consistency.

### set — hash table without values

Structurally similar to dict internals but stores only keys — same O(1) average membership testing, same hashability requirement on elements.

### Big-O summary (average case)

| Op                     | list   | dict          | set  |
| ---------------------- | ------ | ------------- | ---- |
| Access by index/key    | O(1)   | O(1)          | N/A  |
| Search by value        | O(n)   | O(1) (by key) | O(1) |
| Insert at end          | O(1)\* | O(1)          | O(1) |
| Insert at front/middle | O(n)   | N/A           | N/A  |
| Delete                 | O(n)   | O(1)          | O(1) |

\*amortized

## 3. Visual Explanation

```bash
list:  [ptr0][ptr1][ptr2][ptr3]...     (contiguous array, over-allocated)
dict:  hash(key) → bucket index → [key, value] stored in that slot (+ insertion-order side table)
```

## 4. Real-World Example

A common junior mistake: using `if item in my_list:` inside a loop over a large list — O(n) per check, O(n²) overall — when a `set` would make the same check O(1) average, turning a service timeout into a non-issue. This exact pattern (linear search where a hash-based check was possible) is one of the most common real production performance bugs found in code review.

## 5. Best Practices

- Use `set`/`dict` for membership testing, not `list`, when the collection is large or checked repeatedly
- Use `tuple` for fixed, heterogeneous records (like a lightweight struct); use `list` for homogeneous, growable sequences
- Use `collections.deque` (not `list`) when you need efficient insertion/removal at _both_ ends (covered in M2.11)

## 6. Common Mistakes

- `in` checks against a `list` in a hot loop instead of a `set`
- Using a mutable object (like a `list`) as a dict key or set member (raises `TypeError: unhashable type`)
- Assuming dict ordering was guaranteed before 3.7 (it wasn't — a common source of subtle Python 2/early 3 bugs)

## 7. Performance Considerations

This module's Big-O table is the single most practically useful piece of Python knowledge for junior-to-mid performance debugging — most "why is this slow" production bugs in Python trace back to using O(n) list search where an O(1) set/dict lookup was available.

## 8. Security Considerations

Hash-based collections (`dict`, `set`) are the target of **hash-flooding denial-of-service attacks** if hash randomization is disabled — CPython randomizes string hashes by default (`PYTHONHASHSEED`) specifically to mitigate this; never disable hash randomization on internet-facing services.
