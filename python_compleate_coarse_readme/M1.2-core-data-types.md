# Phase 1 · M1.2: Core Data Types & Internal Representation

## 1. Learning Objectives

- Correctly use int, float, complex, bool, str, and NoneType
- Understand how Python represents numbers internally (arbitrary-precision ints, IEEE 754 floats)
- Avoid the classic floating-point precision trap

## 2. Theory

Python's `int` is **arbitrary precision** — it grows as needed (backed by a variable-length digit array in CPython), unlike C's fixed-width `int`. This is _why_ Python never silently overflows integers — a deliberate safety/correctness trade-off costing some performance versus fixed-width native ints.

`float` is a standard **IEEE 754 double-precision** (64-bit) value — the _same_ representation as most languages, meaning the famous `0.1 + 0.2 != 0.3` issue is a hardware/standard property, not a Python quirk.

`bool` is technically a **subclass of `int`** (`True == 1`, `False == 0`) — a historical design choice for backward compatibility when `bool` was added in Python 2.3 (2003), after `int` already existed.

`None` is the sole instance of `NoneType` — a singleton, used as the canonical "no value" sentinel (never use `0`, `""`, or `-1` as a missing-value sentinel when `None` is available and clearer).

### WHY arbitrary-precision ints exist

Languages without them (C, Java `int`) require the programmer to reason about overflow explicitly. Python trades some performance for eliminating an entire bug class — appropriate for a language prioritizing correctness/readability over raw numeric throughput (numeric-heavy work delegates to NumPy's fixed-width arrays instead, covered in Phase 4).

## 3. Visual Explanation

```bash
int:    arbitrary precision  →  [sign][digit][digit][digit]...   (grows as needed)

```

## 4. Real-World Example

Financial software (billing systems, trading platforms) must avoid `float` for currency entirely — `0.1 + 0.2 == 0.30000000000000004` is a real, production-breaking bug class. Production code uses `decimal.Decimal` or integer cents instead.

## 5. Best Practices

- Use `decimal.Decimal` for money/precise arithmetic, never raw `float`
- Use `None` (not sentinel magic values) to represent "absence of value"
- Prefer explicit `isinstance(x, bool)` checks before `isinstance(x, int)` when bool-vs-int distinction matters, since `True` passes `isinstance(True, int)`

## 6. Common Mistakes

- Comparing floats with `==` instead of a tolerance (`math.isclose`)
- Using `float` for money
- Forgetting `bool` is an `int` subclass, causing surprising `dict` key collisions (`{True: 'a', 1: 'b'}` has one key, not two)

## 7. Performance Considerations

Arbitrary-precision int arithmetic is slower than fixed-width for large numbers, and CPU-bound numeric work at scale generally moves to NumPy (fixed-width, vectorized, C-backed) rather than raw Python ints/floats.

## 8. Security Considerations

Financial/precision bugs from float misuse aren't just correctness issues — miscalculated balances or prices are a real business/compliance risk; treat `Decimal` usage as a hard requirement in relevant domains, not a style preference.
