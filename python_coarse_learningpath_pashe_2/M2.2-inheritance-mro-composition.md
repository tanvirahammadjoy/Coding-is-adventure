# Phase 2 · M2.2: Inheritance, MRO, Mixins & Composition

## 1. Learning Objectives
- Use single and multiple inheritance correctly
- Explain C3 linearization (MRO) and predict method resolution order for a given class hierarchy
- Apply "composition over inheritance" judgment in real design decisions

## 2. Theory

### `super()` and the MRO
`super()` doesn't mean "my parent class" — it means "the next class in the **Method Resolution Order**." Python computes MRO using the **C3 linearization algorithm**, producing a single, consistent linear order across a potentially complex multiple-inheritance graph, such that:
- A class always appears before its parents
- If a class inherits from multiple classes, their relative order is preserved

This is *why* multiple inheritance in Python is more predictable than in languages with ambiguous diamond-inheritance resolution (like old-style C++) — but it can still produce genuinely confusing hierarchies if overused.

```python
class A: 
    def greet(self): print("A")
class B(A): 
    def greet(self): print("B"); super().greet()
class C(A): 
    def greet(self): print("C"); super().greet()
class D(B, C): 
    def greet(self): print("D"); super().greet()

D().greet()   # D, B, C, A  — inspect via D.__mro__
```

### Mixins
A **mixin** is a class designed to be combined with others to add a specific piece of behavior, not to stand alone (e.g., `JSONSerializableMixin`, `LoggingMixin`). Mixins lean on multiple inheritance deliberately and are a legitimately Pythonic pattern — distinct from deep "is-a" inheritance chains.

### WHY composition is often preferred
"Composition over inheritance" means giving a class a *reference* to another object rather than inheriting its behavior, when the relationship is "has-a" rather than "is-a." Inheritance couples subclass to superclass implementation details tightly (fragile base class problem) — composition keeps components independently testable/replaceable. This is not a rule against inheritance entirely, but a bias: reach for inheritance for genuine "is-a" type relationships and interface conformance, reach for composition for behavior reuse/assembly.

### WHEN to use each
- Inheritance: genuine "is-a" relationships, or implementing a common interface/ABC (M2.5)
- Mixins: adding a well-isolated, reusable capability across otherwise-unrelated classes
- Composition: "has-a" relationships, or when you want to swap implementations at runtime (e.g., dependency injection, M4.2)

## 4. Real-World Example
Django's class-based views use mixins extensively (`LoginRequiredMixin`, `ListView`) — composing orthogonal behaviors via multiple inheritance in a controlled, well-documented way. Conversely, deep single-inheritance chains (`AdminUser(PowerUser(RegularUser(BaseUser)))`) are a common real anti-pattern flagged in code review, usually better modeled with composition or a role/permission system.

## 5. Best Practices
- Keep inheritance hierarchies shallow (2-3 levels max) where possible
- Use mixins for well-isolated, orthogonal capabilities, not tangled shared state
- Default to composition for "has-a" relationships; reserve inheritance for genuine "is-a" + interface conformance

## 6. Common Mistakes
- Deep inheritance chains that make behavior hard to trace ("where does this method actually come from?")
- Forgetting `super().__init__()` in a subclass, silently skipping parent initialization
- Using inheritance purely for code reuse when composition would be more flexible and testable

## 7. Performance Considerations
Deep MRO chains add a small lookup cost per attribute access (each level checked in order) — rarely significant in practice, but a genuinely deep/wide hierarchy can measurably slow attribute-heavy hot paths; usually a design smell before it's a performance problem.

## 8. Security Considerations
Complex multiple-inheritance hierarchies can obscure which class's `__init__`/validation logic actually runs for a given instance — a real risk in security-sensitive base classes (e.g., an `AuthenticatedMixin`) where an unexpected MRO could cause a security check to be silently skipped; keep such hierarchies simple and well-tested.
