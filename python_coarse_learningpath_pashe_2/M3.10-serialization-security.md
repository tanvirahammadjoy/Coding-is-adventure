# Phase 3 · M3.10: Serialization Deep Dive — pickle, msgpack, protobuf & Security

## 1. Learning Objectives
- Understand how `pickle` works internally and why it's dangerous with untrusted data
- Compare pickle, JSON, msgpack, and protobuf for different use cases
- Apply the correct serialization format decision framework for a given scenario

## 2. Theory

### `pickle` — Python-native, powerful, dangerous
`pickle` serializes **almost any** Python object (including custom classes, closures in some cases, complex nested structures) by recording a sequence of instructions to **reconstruct** the object — critically, unpickling can involve calling arbitrary constructors/`__reduce__` methods, which means **unpickling untrusted data can execute arbitrary code**. This is not a theoretical risk — it's a well-documented, actively-exploited real-world vulnerability class (`pickle.loads()` on attacker-controlled data is equivalent, in risk, to `eval()` on attacker-controlled strings, M1.9's security note extended to its full seriousness here).

```python
# NEVER do this with data from an untrusted source (network, user upload, external API)
data = pickle.loads(untrusted_bytes)   # can execute arbitrary code during deserialization
```

WHEN pickle IS appropriate: serializing/deserializing data **you fully control both ends of** — e.g., `multiprocessing`'s internal IPC (M3.4), caching your own application's internal objects to disk/Redis where only your own trusted code ever writes the cache.

### JSON — safe, portable, limited
Covered in M2.12 — safe for untrusted data (parsing JSON cannot execute code), universally portable across languages, but limited to a smaller set of types (no native datetime/Decimal/custom-class support without manual encoding).

### `msgpack` — binary, compact, JSON-like safety
A binary serialization format with a similar type model to JSON (safe to parse untrusted data) but significantly more compact and faster to encode/decode — a good choice when you need JSON-like safety/portability but with better performance/size, common in high-throughput internal service communication.

### Protocol Buffers (protobuf) — schema-first, cross-language, fast
Requires defining a schema (`.proto` file) upfront, generating strongly-typed serialization code — used heavily in gRPC (Phase 4's M4.8) and large-scale distributed systems (originated at Google) where schema evolution, strict typing, and cross-language interop (Python service talking to a Go or Java service) matter. Higher upfront cost (schema definition, codegen step) but strong guarantees and excellent performance.

### Decision framework
| Need | Choice |
|---|---|
| Human-readable, universal, safe for untrusted data | JSON |
| Compact/fast, still safe for untrusted data, similar type model to JSON | msgpack |
| Strict schema, cross-language, high-performance RPC | protobuf (usually with gRPC) |
| Internal-only, full trust on both ends, need to serialize arbitrary Python objects | pickle |
| NEVER | pickle on ANY data that could originate from outside your own trusted process boundary |

## 3. Visual Explanation
```
pickle.loads(bytes)  →  can execute __reduce__/constructors during reconstruction
                          → arbitrary code execution possible if bytes are attacker-controlled

json.loads(text)     →  pure data parsing, no code execution path
                          → safe even for fully untrusted input
```

## 4. Real-World Example
A well-documented, real-world vulnerability class: services that cached data in Redis using `pickle` for convenience, then later exposed a code path where an attacker could write attacker-controlled bytes into that Redis key (e.g., via a separate injection vulnerability, or an improperly secured Redis instance) — the moment the service read and `pickle.loads()`-ed that data, arbitrary attacker code executed with the service's privileges. This exact pattern has appeared in real CVEs and security advisories.

## 5. Best Practices
- Never `pickle.loads()` data that could have originated, even indirectly, from outside your fully-trusted process boundary
- Default to JSON for anything crossing a trust boundary (API responses, user data, external cache accessible to other processes/services)
- Use msgpack when JSON's performance/size becomes a genuine bottleneck, keeping the same safety properties
- Use protobuf/gRPC for cross-language, schema-strict, high-performance internal service communication

## 6. Common Mistakes
- Using `pickle` for caching data in a shared store (Redis, Memcached) that other, less-trusted processes/services can also write to
- Assuming `pickle` is "just like JSON but for Python objects" without understanding the security implications of that convenience
- Over-engineering with protobuf/gRPC for a simple internal tool where JSON would have been perfectly sufficient

## 7. Performance Considerations
Pickle and msgpack are both meaningfully faster and more compact than JSON for large/complex data structures — but the safety trade-off (pickle's arbitrary-code-execution risk) must dominate the decision whenever any degree of trust ambiguity exists; never choose pickle for performance reasons alone when the data crosses any trust boundary.

## 8. Security Considerations
This entire module is fundamentally a security module — `pickle.loads()` on untrusted data is one of the most severe, most easily-avoidable vulnerability classes in the Python ecosystem; the fix is simply institutional discipline (never do it) rather than any technical mitigation, making code review vigilance on this specific pattern extremely high-value.
