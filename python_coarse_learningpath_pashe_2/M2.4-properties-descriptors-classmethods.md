# Phase 2 · M2.4: Properties, Descriptors, classmethod & staticmethod

## 1. Learning Objectives
- Use `@property` to control attribute access without breaking the calling API
- Explain the descriptor protocol underlying `@property`, methods, and `@classmethod`/`@staticmethod`
- Choose correctly between instance methods, classmethods, and staticmethods

## 2. Theory

### `@property`
```python
class Circle:
    def __init__(self, radius): self._radius = radius
    @property
    def radius(self):
        return self._radius
    @radius.setter
    def radius(self, value):
        if value < 0: raise ValueError("radius must be non-negative")
        self._radius = value
    @property
    def area(self):
        return 3.14159 * self._radius ** 2
```
`@property` lets `circle.radius` look like plain attribute access while actually running code (validation, computed values) — critical because it means you can **start** with a plain public attribute and **later** add validation/computation without breaking any caller's code (`obj.attr` syntax stays identical). This is *why* Python doesn't push getter/setter boilerplate on every attribute the way older Java conventions do — properties let you add that layer only when actually needed.

### The descriptor protocol (what `@property` is built on)
A **descriptor** is any object implementing `__get__`, `__set__`, and/or `__delete__`, placed as a *class* attribute. When you access `instance.attr`, Python checks if the class attribute is a descriptor and, if so, calls its `__get__` instead of returning it directly. `@property` is literally a built-in descriptor implementation. Even ordinary **functions are descriptors** — this is *why* `instance.method` automatically becomes a "bound method" (function's `__get__` binds `self`) — the exact mechanism underlying M2.1's `self` explanation.

### classmethod vs staticmethod vs instance method
- **Instance method** (`def foo(self)`) — operates on a specific instance
- **`@classmethod`** (`def foo(cls)`) — operates on the class itself; commonly used for alternative constructors (`Point.from_tuple((1,2))`)
- **`@staticmethod`** (`def foo()`) — no implicit first argument; a plain function namespaced under the class, for utility logic that's conceptually related but needs neither `self` nor `cls`

### WHEN to use classmethod for constructors
`@classmethod` alternative constructors (`from_json`, `from_tuple`) are idiomatic Python — cleaner than overloading `__init__` with many optional parameters or type-checking argument shapes inside a single constructor.

## 4. Real-World Example
ORMs (Django models, SQLAlchemy) use the descriptor protocol extensively — `model.field` looks like plain attribute access but actually triggers database-aware logic (lazy loading, type coercion, change tracking) behind the scenes via custom descriptors, entirely invisible to the API consumer.

## 5. Best Practices
- Start with plain public attributes; add `@property` only when validation/computation is actually needed (don't pre-emptively wrap everything in getters/setters, Java-style)
- Use `@classmethod` for alternative constructors instead of complex `__init__` overloading
- Use `@staticmethod` sparingly — if a function doesn't need `self` or `cls`, consider whether it should be a module-level function instead

## 6. Common Mistakes
- Pre-emptively wrapping every attribute in `@property` "just in case," adding needless boilerplate
- Forgetting the setter is a separate `@x.setter`-decorated method with the *same name*
- Confusing `@classmethod` and `@staticmethod` — using `@staticmethod` when the method actually needs to know its class (e.g., for subclass-aware alternative constructors, `@classmethod` is required so `cls` resolves to the actual subclass)

## 7. Performance Considerations
Property access has a small overhead versus plain attribute access (a function call under the hood) — negligible for almost all code, but relevant in extremely hot loops accessing the same computed property millions of times; consider caching (`functools.cached_property`) for expensive computed properties that don't change.

## 8. Security Considerations
`@property` setters are a natural, idiomatic place to enforce validation invariants (e.g., rejecting negative balances, sanitizing input) transparently to callers — a legitimate security-relevant pattern for maintaining object invariants throughout an object's lifetime, not just at construction.
