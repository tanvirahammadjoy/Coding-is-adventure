# Phase 2 · M2.10: Testing — pytest, Fixtures, Mocking & TDD

## 1. Learning Objectives
- Write effective tests using pytest (fixtures, parametrization, assertions)
- Use `unittest.mock` correctly to isolate units under test
- Apply TDD as a workflow, and measure/interpret test coverage

## 2. Theory

### Why automated testing exists
Manual testing doesn't scale — it's slow, inconsistent, and gets skipped under deadline pressure, exactly when it matters most. Automated tests are **executable specifications**: they encode expected behavior once and verify it forever, catching regressions the instant they're introduced (especially valuable in CI, before code reaches production).

### pytest vs unittest
`unittest` (stdlib) uses xUnit-style classes (`TestCase`, `self.assertEqual`). **pytest** (third-party, but the de facto standard) uses plain functions with `assert`, richer fixtures, better failure output, and a huge plugin ecosystem — it's become the dominant choice in modern Python (2020s onward) for its ergonomics, though it can also run `unittest`-style tests unchanged.

```python
def test_deposit_increases_balance():
    account = BankAccount(owner="Alice", balance=Decimal("100"))
    account.deposit(Decimal("50"))
    assert account.balance == Decimal("150")
```

### Fixtures — reusable setup/teardown
```python
import pytest

@pytest.fixture
def account():
    return BankAccount(owner="Alice", balance=Decimal("100"))

def test_deposit(account):
    account.deposit(Decimal("50"))
    assert account.balance == Decimal("150")
```
Fixtures are pytest's answer to setup/teardown — a function decorated `@pytest.fixture`, injected into any test that names it as a parameter. Fixture scope (`function`, `module`, `session`) controls how often it's recreated, letting expensive setup (e.g., a test database connection) be shared safely across many tests when appropriate.

### Parametrization
```python
@pytest.mark.parametrize("amount,expected", [(50, 150), (0, 100), (-10, 90)])
def test_deposit_various(account, amount, expected):
    account.deposit(Decimal(amount))
    assert account.balance == Decimal(expected)
```
Runs the same test logic against multiple inputs, avoiding copy-pasted near-duplicate test functions.

### Mocking — isolating the unit under test
```python
from unittest.mock import Mock, patch

def test_notifies_on_large_withdrawal():
    notifier = Mock()
    account = BankAccount(owner="Alice", balance=Decimal("1000"), notifier=notifier)
    account.withdraw(Decimal("900"))
    notifier.send.assert_called_once()
```
`Mock`/`patch` replace real dependencies (network calls, databases, external services) with controllable fakes — essential for **unit** tests, which should test one component's logic in isolation, fast and deterministic, without hitting real external systems.

### TDD (Test-Driven Development)
Write a failing test first (red), write the minimal code to pass it (green), then refactor (refactor) — a discipline that keeps tests genuinely driving design rather than being retrofitted afterward, though many production teams use it selectively rather than universally.

## 3. Visual Explanation
```
Unit test        →  tests ONE function/class, dependencies mocked, fast, isolated
Integration test  →  tests multiple components together (e.g., real DB), slower
End-to-end test    →  tests the whole system as a user would, slowest, most realistic
                       (the "testing pyramid": many unit tests, fewer integration, fewest e2e)
```

## 4. Real-World Example
Production incident postmortems frequently trace back to a code path with zero test coverage — a change to an "obviously safe" utility function silently broke an unrelated feature that depended on its exact behavior. Comprehensive test suites (with good coverage of edge cases, not just happy paths) are one of the highest-leverage practices for preventing exactly this class of incident.

## 5. Best Practices
- Test behavior, not implementation details (tests shouldn't break from harmless refactors)
- Mock external dependencies in unit tests; use real dependencies (or realistic fakes) in integration tests
- Aim for meaningful coverage of edge cases and error paths, not just the happy path, over chasing a raw coverage percentage
- Keep tests fast — a slow test suite gets skipped/ignored under pressure

## 6. Common Mistakes
- Testing implementation details so rigidly that any refactor breaks tests even when behavior is unchanged
- Over-mocking, to the point tests no longer verify anything real
- Chasing 100% coverage as a vanity metric while missing genuinely important edge cases
- Flaky tests (nondeterministic failures) left unfixed, eroding trust in the whole suite

## 7. Performance Considerations
A slow test suite is a real productivity cost at scale — parallelize test runs (`pytest-xdist`), keep unit tests genuinely fast (no real I/O), and reserve slow integration/e2e tests for a separate, less-frequently-run CI stage.

## 8. Security Considerations
Security-critical logic (auth checks, permission boundaries, input validation) deserves disproportionately thorough test coverage, including deliberately adversarial test cases (attempting to bypass a check) — treat security-relevant tests as a hard CI gate, not optional.
