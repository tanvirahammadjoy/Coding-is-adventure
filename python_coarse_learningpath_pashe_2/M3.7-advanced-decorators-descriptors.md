# Phase 3 · M3.7: Advanced Decorators & Descriptors in Production

## 1. Learning Objectives
- Build class decorators as an alternative to metaclasses for many use cases
- Combine descriptors with decorators to build production-grade validation/caching layers
- Recognize these patterns as they appear inside real ORMs and frameworks

## 2. Theory

### Class decorators — the middle ground
```python
def register(cls):
    REGISTRY[cls.__name__] = cls
    return cls

@register
class Handler: ...
```
A class decorator is a function applied to a **class** rather than a function — same underlying mechanism as M2.6's function decorators (`cls = register(cls)`), but operating one level up. This is often a simpler, more explicit alternative to `__init_subclass__` or a metaclass (M3.6) for the common case of "do something with a class once it's fully defined," without the deeper machinery.

### `functools.lru_cache` as a production caching layer
```python
from functools import lru_cache

@lru_cache(maxsize=1024)
def expensive_lookup(key: str) -> Result:
    return db.query(key)
```
Real production services use `lru_cache` extensively for memoizing expensive, pure (side-effect-free, deterministic) function calls — but with real caveats: `maxsize` MUST be bounded in long-running services (unbounded caches are a memory leak in disguise); the cache is **process-local** (doesn't help across multiple worker processes — that needs a shared cache like Redis, Phase 5); and cached functions must have **hashable** arguments (M2.3's `__hash__` lesson resurfaces here directly).

### Descriptor-based validation (production ORM pattern)
```python
class ValidatedField:
    def __init__(self, validator):
        self.validator = validator
    def __set_name__(self, owner, name):
        self.name = "_" + name          # __set_name__ (PEP 487) tells the descriptor its own attribute name
    def __get__(self, instance, owner):
        return getattr(instance, self.name, None)
    def __set__(self, instance, value):
        if not self.validator(value):
            raise ValueError(f"invalid value for {self.name}: {value}")
        setattr(instance, self.name, value)

class User:
    age = ValidatedField(lambda v: 0 <= v <= 150)
```
This is, structurally, exactly how ORM field validation (Django, SQLAlchemy) and dataclass-adjacent validation libraries implement per-field validation transparently — `user.age = -5` raises immediately, at the assignment site, with the validation logic fully reusable across any number of fields/classes (extending M2.4's custom-descriptor challenge exercise into a genuinely production-shaped pattern).

### `__set_name__` — descriptors learning their own name
Added in PEP 487 specifically to solve an awkward historical problem: a descriptor instance, created once at class-definition time, previously had no clean way to know what attribute name it was assigned to. `__set_name__(self, owner, name)` is called automatically by the class-creation machinery, solving this cleanly.

## 3. Visual Explanation
```
class User:
    age = ValidatedField(...)   ← descriptor instance, created ONCE at class definition

user1.age = 30    →  ValidatedField.__set__(descriptor, user1, 30)   → validated, stored on user1
user2.age = -5    →  ValidatedField.__set__(descriptor, user2, -5)   → raises ValueError
   (ONE descriptor instance shared across all User instances — validation logic, not data, is shared)
```

## 4. Real-World Example
Pydantic (a widely-used validation library) and Django's model fields both use descriptor-like mechanisms extensively under the hood to make `instance.field = value` transparently trigger type coercion and validation — application developers get a clean, Pythonic attribute-assignment API while the library does substantial work behind `__set__`, entirely invisible at the call site.

## 5. Best Practices
- Always bound `lru_cache`'s `maxsize` in long-running services
- Use `__set_name__` when a descriptor needs to know its own attribute name, rather than requiring it be passed manually
- Reach for a class decorator before a metaclass when the need is simpler (one-time class-level action, not deep namespace manipulation)

## 6. Common Mistakes
- Unbounded `lru_cache` in a long-running service, causing gradual memory growth (revisits M3.1's memory-leak lessons)
- Forgetting `lru_cache`'d functions must have hashable arguments — passing a `list` or `dict` argument raises `TypeError`
- Writing a descriptor without `__set_name__` and hardcoding the attribute name, breaking if the descriptor is ever reused under a different attribute name

## 7. Performance Considerations
`lru_cache` genuinely trades memory for CPU time — profile first (Phase 3's M3.8) to confirm a function is actually a hot, expensive, repeatedly-called-with-the-same-arguments bottleneck before reaching for it; caching cheap functions can add overhead (cache lookup cost) without meaningful benefit.

## 8. Security Considerations
Caching functions that take user-controlled input as cache keys (`lru_cache` on a function processing request data) can be a resource-exhaustion vector if an attacker can generate unbounded unique cache keys — always bound `maxsize`, and consider whether caching untrusted-input-keyed data is appropriate at all versus a request-scoped cache instead.
