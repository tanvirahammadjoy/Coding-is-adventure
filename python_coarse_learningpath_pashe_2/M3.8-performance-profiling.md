# Phase 3 · M3.8: Performance Profiling & Optimization

## 1. Learning Objectives
- Profile Python code correctly using `cProfile`, `line_profiler`, and `py-spy`
- Apply the "measure, don't guess" discipline to optimization work
- Know when to optimize algorithmically vs when to drop to native code

## 2. Theory

### The cardinal rule: measure before optimizing
"Premature optimization is the root of all evil" (Donald Knuth) — intuition about what's slow is **frequently wrong**, even for experienced engineers. The correct workflow is always: **profile → identify the actual bottleneck → optimize that specific thing → re-measure to confirm improvement**. Optimizing code that isn't actually the bottleneck wastes effort and adds complexity for no benefit.

### `cProfile` — function-level profiling
```bash
python -m cProfile -s cumulative myscript.py
```
Reports time spent in each function (including cumulative time in functions it calls) — the right first step for "where is time going, at a coarse level." Low overhead enough for regular use, but doesn't show line-by-line detail within a function.

### `line_profiler` — line-level profiling
```python
@profile   # requires kernprof to run
def slow_function():
    ...
```
Once `cProfile` identifies a slow function, `line_profiler` shows **exactly which lines** inside it consume the time — essential for pinpointing the actual bottleneck within a large function, rather than guessing.

### `memory_profiler` / `tracemalloc`
For memory (not just CPU time) profiling — `tracemalloc` (stdlib) tracks memory allocations by line/traceback, useful for finding unexpected memory growth (connecting back to M3.1's memory model).

### `py-spy` — production profiling without code changes
A sampling profiler that can attach to an **already-running** Python process (including in production, with low overhead) without requiring any code modification or restart — invaluable for diagnosing a live production performance issue without redeploying instrumented code.

### `timeit` — micro-benchmarking
```python
import timeit
timeit.timeit("x = [i for i in range(1000)]", number=10000)
```
For comparing small code snippets' performance precisely (accounting for measurement noise via repeated runs) — the right tool for "is approach A or B faster" questions at a small scale, distinct from whole-program profiling.

### The optimization decision ladder
1. **Algorithmic** — is there a better Big-O approach (M1.6's lessons)? Usually the biggest win, and free (no added complexity/dependencies)
2. **Better stdlib/library usage** — the right data structure, `deque` instead of `list`, vectorized NumPy instead of a loop (M2.11/M2.12)
3. **Caching/memoization** — avoid redundant computation (M3.7)
4. **Concurrency/parallelism** — if the workload genuinely allows it (M3.3-M3.5)
5. **Drop to native code** — Cython/C extensions/Rust (M3.9), only after the above are exhausted and profiling shows a genuine, unavoidable CPU-bound hotspot

## 3. Visual Explanation
```
cProfile   →  "function X takes 80% of total time"           (coarse, function-level)
    │
line_profiler →  "line 47 inside function X takes 60% of X's time"  (fine, line-level)
    │
Now you know EXACTLY where to focus optimization effort — not before.
```

## 4. Real-World Example
A team assumes a slow API endpoint is CPU-bound and spends a week optimizing a computation function — profiling later reveals 95% of the time was actually spent in an unindexed database query, not the Python code at all. This is an extremely common, entirely avoidable real-world story — profiling first would have redirected effort correctly from day one, saving the wasted week.

## 5. Best Practices
- Always profile before optimizing — never optimize based on intuition alone
- Re-measure after every optimization to confirm actual improvement (some "obvious" optimizations don't help, or even hurt)
- Optimize algorithmically first, drop to native code last
- Keep a profiling step in your regular development workflow for performance-sensitive code, not just as a one-off incident response

## 6. Common Mistakes
- Optimizing code that "feels slow" without profiling, often optimizing the wrong thing entirely
- Micro-optimizing Python-level code when the actual bottleneck is I/O (network/database), where Python-level optimization is irrelevant
- Adding complex caching/concurrency for a performance problem that a simple algorithmic fix (correct data structure) would have solved more simply

## 7. Performance Considerations
This entire module IS performance considerations — but specifically: profiling tools themselves have overhead (`cProfile`'s instrumentation, `line_profiler`'s per-line overhead) — use `py-spy`'s sampling approach for production environments where instrumentation overhead is unacceptable, reserving `cProfile`/`line_profiler` for development/staging investigation.

## 8. Security Considerations
`py-spy` (and similar tools attaching to running processes) require appropriate OS-level permissions to attach to another process — a real security consideration for who can run such tools against production services, since process memory inspection could expose sensitive in-memory data (credentials, user data) if misused.
