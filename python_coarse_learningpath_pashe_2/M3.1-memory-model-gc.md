# Phase 3 · M3.1: Python's Memory Model — Reference Counting & Garbage Collection

## 1. Learning Objectives
- Explain CPython's two-layer memory management: reference counting + generational GC
- Diagnose memory leaks using `gc` and `sys.getrefcount`
- Use `__slots__` and weak references appropriately

## 2. Theory

### Reference counting — the primary mechanism
Every CPython object carries a `refcount` (visible via `sys.getrefcount`, always +1 due to the argument reference itself). When an object is bound to a name, passed as an argument, or stored in a container, its refcount increments; when a reference goes out of scope, is reassigned, or deleted, it decrements. **When refcount hits zero, the object is deallocated immediately** — this is *why* CPython's memory reclamation is largely deterministic and immediate, unlike languages with purely tracing garbage collectors (Java, Go) where deallocation timing is unpredictable.

### The problem reference counting alone can't solve: cycles
```python
a = {}
b = {}
a["b"] = b
b["a"] = a
del a, b   # refcount of each dict is still 1 (they reference each other) — never hits zero!
```
This is *why* CPython also has a **generational garbage collector** (the `gc` module) — specifically to detect and collect **reference cycles** that pure refcounting can never clean up. It periodically scans for groups of objects only reachable from each other (not from any live root), and collects them.

### Generational GC
Objects are grouped into 3 generations (0, 1, 2) based on survival — new objects start in gen 0; objects surviving a collection get promoted. Gen 0 is collected most frequently (most objects die young — the "generational hypothesis," true across most languages/runtimes), gen 2 least frequently. This is a performance optimization: scanning all objects every time would be wasteful when most garbage is short-lived.

### `__slots__`
```python
class Point:
    __slots__ = ("x", "y")   # no per-instance __dict__
    def __init__(self, x, y): self.x, self.y = x, y
```
By default, instances have a `__dict__` (a hash table) for attributes — flexible but memory-heavy. `__slots__` allocates fixed-size storage instead, saving significant memory (especially meaningful with millions of instances) and slightly speeding attribute access — at the cost of losing dynamic attribute assignment and needing to redeclare slots in each subclass.

### Weak references
`weakref.ref(obj)` holds a reference that does NOT increment refcount — used for caches/observers that shouldn't keep an object alive just by referencing it, letting the object be garbage collected normally when no *strong* references remain.

## 3. Visual Explanation
```
x = [1, 2, 3]     refcount=1
y = x             refcount=2
del x             refcount=1
del y             refcount=0  →  deallocated immediately

Cycle: a → b → a, no external reference  →  refcount never 0  →  gen-GC required to collect
```

## 4. Real-World Example
A common real production memory leak: registering event-handler callbacks that hold a strong reference back to the object that registered them (e.g., a widget referencing a controller which references the widget) — refcounting alone never frees this cycle without the GC running; in performance-critical long-running services, understanding this distinction is essential for correctly diagnosing "why is memory growing" incidents (versus assuming it's always a "real" leak requiring architecture changes).

## 5. Best Practices
- Use `__slots__` for high-volume, simple data-holder classes (millions of instances)
- Use `weakref` for caches/observer patterns to avoid unintentionally keeping objects alive
- Avoid `__del__` methods except when absolutely necessary — they interact poorly with cyclic GC and can delay collection or cause hard-to-debug ordering issues

## 6. Common Mistakes
- Assuming Python has "no memory leaks" because of GC — reference cycles combined with `__del__` methods, or objects unexpectedly kept alive by caches/closures, are real, common leaks
- Adding `__slots__` to a class hierarchy inconsistently (forgetting to declare slots in every subclass), silently reintroducing `__dict__` and losing the memory benefit
- Using strong references for cache values that should allow garbage collection when otherwise unused (should use `weakref` or a bounded/evicting cache instead)

## 7. Performance Considerations
`__slots__` measurably reduces memory footprint for large numbers of instances and speeds attribute access — a real, worthwhile optimization for the right shape of workload (many simple objects), not a universal default (adds rigidity, breaks multiple inheritance combining slotted classes in some cases).

## 8. Security Considerations
Memory-leak-driven resource exhaustion (a long-running service slowly consuming all available memory due to an unintended reference cycle or unbounded cache) is itself a denial-of-service risk in production — treat memory growth monitoring (Phase 5's M5.5) as a security-adjacent concern, not purely an ops metric.

## 9. Hands-On Exercises
1. Create a reference cycle deliberately, confirm via `gc.collect()` return value that the GC (not refcounting) is what reclaims it
2. Add `__slots__` to a simple data class and measure the memory difference (via `sys.getsizeof` or a library like `pympler`) versus the same class without slots, at scale (10,000+ instances)
3. Implement a simple cache using `weakref.WeakValueDictionary` and demonstrate entries disappearing once the only strong reference is dropped

## 10. Mini Project
