# Phase 3 · M3.5: Async Programming — `asyncio` Deep Dive

## 1. Learning Objectives
- Explain the event loop model and how it differs fundamentally from threading
- Write correct `async`/`await` code, including concurrent task execution
- Choose correctly between asyncio, threading, and multiprocessing for a given workload

## 2. Theory

### The event loop model
`asyncio` achieves concurrency **within a single thread** via **cooperative multitasking**: coroutines voluntarily yield control (at `await` points) back to an event loop, which then runs other ready coroutines. This is fundamentally different from threading's **preemptive** model (the OS/GIL can switch threads at almost any point) — with asyncio, a coroutine runs uninterrupted until it explicitly awaits something, making certain classes of race conditions (mid-statement interleaving) impossible **as long as you never block synchronously inside a coroutine**.

### `async`/`await` mechanics
```python
async def fetch(url):
    async with aiohttp.ClientSession() as session:
        async with session.get(url) as resp:
            return await resp.text()

async def main():
    results = await asyncio.gather(fetch(url1), fetch(url2), fetch(url3))
```
`async def` defines a **coroutine function** — calling it doesn't run the body; it returns a coroutine object (similar to how calling a generator function returns a generator, M2.7 — coroutines are, mechanically, built on the same underlying machinery). `await` suspends the current coroutine until the awaited operation completes, yielding control to the event loop, which can run other coroutines in the meantime. `asyncio.gather` runs multiple coroutines **concurrently** (not in parallel — still one thread, one GIL), dramatically speeding up I/O-bound work with many outstanding requests.

### The cardinal sin: blocking calls inside async code
```python
async def bad():
    time.sleep(5)          # BLOCKS THE ENTIRE EVENT LOOP — nothing else runs for 5 seconds!
async def good():
    await asyncio.sleep(5)  # yields control, other coroutines run during the wait
```
Any synchronous, blocking call (`time.sleep`, a synchronous `requests.get`, blocking file I/O) inside a coroutine **freezes the entire event loop** — every other concurrent task stalls. This is *the* most common and most damaging asyncio mistake in production code, and often subtle (a library call that "just" does file I/O internally, buried three layers deep in a call chain).

### Structured concurrency — `asyncio.TaskGroup` (3.11+)
```python
async def main():
    async with asyncio.TaskGroup() as tg:
        tg.create_task(fetch(url1))
        tg.create_task(fetch(url2))
    # all tasks guaranteed complete (or an exception propagated) by here
```
`TaskGroup` is the modern, preferred replacement for manually tracking a list of tasks and `asyncio.gather` in many cases — it guarantees proper cleanup/cancellation if one task fails, addressing a real historical pain point (orphaned tasks, swallowed exceptions) in earlier asyncio patterns.

### asyncio vs threading vs multiprocessing — decision framework
| Workload | Best tool | Why |
|---|---|---|
| Many concurrent I/O ops (network, DB) | asyncio | Lowest overhead, scales to thousands of concurrent operations |
| Moderate I/O concurrency, existing sync libraries | threading | Simpler mental model, works with non-async libraries |
| CPU-bound parallel work | multiprocessing | Only true option to bypass the GIL |
| Mixed: some CPU-bound work inside an async app | asyncio + `run_in_executor`/`ProcessPoolExecutor` | Offload CPU work to a thread/process pool without blocking the event loop |

## 3. Visual Explanation
```
Event loop (single thread):
 t=0: Task A starts, awaits network response  → loop switches to Task B
 t=1: Task B starts, awaits network response  → loop switches to Task C
 t=2: Task C starts, awaits network response  → loop checks: any responses ready?
 t=3: Task A's response arrives → loop resumes Task A exactly where it left off
```

## 4. Real-World Example
Modern async web frameworks (FastAPI, when used with async route handlers) can handle thousands of concurrent slow-database-query requests on a single process/thread far more efficiently than a traditional threaded model, because each request spends most of its time *waiting* (I/O), not computing — but a single accidentally-synchronous call (e.g., a non-async ORM call inside an async route) can silently degrade the entire server's throughput, a very real, very common production incident class in async Python services.

## 5. Best Practices
- Never call a blocking/synchronous function directly inside a coroutine — use an async-native library, or offload via `loop.run_in_executor`
- Use `asyncio.TaskGroup` (3.11+) over manual task-list management for structured, safe concurrent execution
- Use `asyncio.timeout()` (3.11+) to bound how long you'll wait on any single operation, preventing one slow dependency from hanging everything

## 6. Common Mistakes
- Calling a blocking function inside async code, freezing the event loop for all concurrent tasks
- Using `asyncio.gather` without `return_exceptions=True` when you want partial results even if one task fails, and not handling exception propagation intentionally
- Forgetting to `await` a coroutine (creates a coroutine object that never actually runs — Python emits a `RuntimeWarning: coroutine was never awaited`, a very common early-async bug)
- Mixing sync and async code carelessly without understanding the boundary (e.g., calling `asyncio.run()` inside code that's already running inside an event loop)

## 7. Performance Considerations
Asyncio has dramatically lower per-task overhead than threading for I/O-bound concurrency (no OS thread creation cost, no context-switch cost) — it scales to tens of thousands of concurrent operations where threading would exhaust OS resources; but a single blocking call anywhere in the call graph can silently negate the entire architecture's benefit, making disciplined library selection (fully async-native stack) critical.

## 8. Security Considerations
`asyncio.timeout()`/bounded waits are a meaningful defense against slow-loris-style resource exhaustion attacks (a malicious or misbehaving client/dependency holding a connection open indefinitely) — always bound external calls in async services rather than awaiting indefinitely.
