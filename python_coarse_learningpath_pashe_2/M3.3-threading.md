# Phase 3 · M3.3: Concurrency with `threading`

## 1. Learning Objectives
- Use the `threading` module correctly for I/O-bound concurrency
- Identify and prevent race conditions using locks
- Recognize deadlock-prone patterns and avoid them

## 2. Theory

### Basic threading
```python
import threading

def worker(n):
    print(f"working on {n}")

threads = [threading.Thread(target=worker, args=(i,)) for i in range(5)]
for t in threads: t.start()
for t in threads: t.join()   # wait for all to finish
```

### Race conditions
When multiple threads read-modify-write shared state without synchronization, operations can interleave unpredictably:
```python
counter = 0
def increment():
    global counter
    for _ in range(100_000):
        counter += 1     # NOT atomic! read, add, write — a thread can be interrupted mid-operation
```
Running this with 2 threads typically produces a final `counter` value **less than** 200,000 — a classic, reproducible race condition, because `counter += 1` is actually three separate bytecode steps (load, add, store), and the GIL can switch threads between any of them.

### Locks
```python
lock = threading.Lock()
def increment():
    global counter
    for _ in range(100_000):
        with lock:            # context manager (M2.8) — acquires and guarantees release
            counter += 1
```
A `Lock` ensures only one thread executes the protected section at a time, making the read-modify-write atomic **relative to other threads holding the same lock**.

### Deadlock
Occurs when two threads each hold a lock the other needs:
```
Thread A: holds Lock1, waits for Lock2
Thread B: holds Lock2, waits for Lock1
→ both wait forever
```
**Prevention**: always acquire multiple locks in a consistent, global order across all threads; prefer higher-level primitives (`Queue`, `RLock` when reentrancy is needed) over manual multi-lock juggling where possible.

### Thread pools
`concurrent.futures.ThreadPoolExecutor` provides a higher-level, easier-to-use API than raw `threading.Thread` management for the common "run N tasks across a pool of worker threads" pattern — generally preferred over manual thread management for application code.

## 3. Visual Explanation
```
Without lock:  T1: read(0)         T1: write(1)
               T2:      read(0)              T2: write(1)     ← lost update! should be 2
With lock:     T1: [acquire][read 0, write 1][release]
               T2:                                     [acquire][read 1, write 2][release]
```

## 4. Real-World Example
A real production bug class: a shared in-memory counter/cache updated from multiple request-handling threads without a lock, producing subtly wrong metrics or corrupted cache state under load — invisible in low-traffic testing, appearing only under concurrent production load, making it a notoriously hard bug to reproduce and debug without understanding race conditions explicitly.

## 5. Best Practices
- Prefer `concurrent.futures.ThreadPoolExecutor` over raw `Thread` management for application code
- Protect ALL shared mutable state accessed from multiple threads with a lock (or avoid shared mutable state entirely via message-passing with `queue.Queue`)
- Always acquire multiple locks in a consistent order across the whole codebase to prevent deadlock
- Use `queue.Queue` (thread-safe by design) for producer/consumer patterns instead of manually-locked shared lists

## 6. Common Mistakes
- Assuming simple operations (`+=`, `.append()`) are atomic — they generally aren't, when other threads can interleave
- Forgetting to protect a piece of shared state because "it's just a simple read" (reads can race with concurrent writes too)
- Holding locks longer than necessary, serializing work that didn't need to be serialized, eroding the benefit of threading
- Inconsistent lock-acquisition order across different code paths, causing intermittent deadlocks

## 7. Performance Considerations
Given the GIL (M3.2), threading's performance benefit is specifically for I/O-bound work; over-locking (holding locks around I/O operations, or around more code than strictly necessary) can serialize work that should have run concurrently, eroding or eliminating the intended benefit — lock scope should be as narrow as correctness allows.

## 8. Security Considerations
Race conditions in security-sensitive code (e.g., a check-then-act pattern for authorization, or a rate-limiter's counter) can be exploited as a **TOCTOU (time-of-check to time-of-use)** vulnerability — an attacker deliberately racing requests to bypass a check that assumed atomicity it didn't actually have; security-critical shared state needs the same rigorous locking discipline as any other correctness-critical shared state, arguably more.
