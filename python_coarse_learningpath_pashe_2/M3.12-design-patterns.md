# Phase 3 · M3.12: Design Patterns in Python

## 1. Learning Objectives
- Implement common Gang-of-Four patterns idiomatically in Python
- Recognize when Python's language features make a classical pattern unnecessary
- Avoid pattern over-application ("when all you have is a hammer...")

## 2. Theory

### WHY design patterns need Python-specific adaptation
The classic Gang-of-Four patterns (1994) were designed for statically-typed languages (originally C++/Smalltalk examples) without first-class functions, duck typing, or Python's dynamic features — several patterns that require significant boilerplate in those languages are **trivial or unnecessary** in Python. Recognizing this is itself a mark of Python maturity; blindly porting Java-style pattern implementations into Python is a common intermediate-engineer mistake (verbose, unidiomatic code).

### Patterns that stay genuinely useful in Python
- **Strategy** — trivially implemented via first-class functions (M2.6) instead of a class hierarchy of `Strategy` subclasses; pass a function/callable directly
- **Observer** — natural fit for Python (a list of callback functions, or the `__init_subclass__`/decorator-based registration from M3.6/M3.7)
- **Decorator** (the pattern, distinct from Python's `@decorator` syntax, though related in spirit) — Python's actual decorator syntax (M2.6) often directly implements this pattern's intent more concisely than the classical class-wrapping approach
- **Factory** — often simplified via `@classmethod` alternative constructors (M2.4) rather than a separate Factory class hierarchy
- **Singleton** — often better replaced by a module-level instance (modules are already singletons, per M1.11's import-caching lesson) than a class-based Singleton pattern
- **Context Manager** (Python-specific, not GoF) — arguably Python's own distinctive contribution to this space, covered fully in M2.8

### Patterns to be skeptical of in Python
- **Builder** — often unnecessary given keyword arguments and default values; genuinely useful mainly for complex, multi-step, validated construction
- **Visitor** — genuinely useful for certain structural problems (AST traversal) but often over-applied; `match`/`case` (M1.4) frequently achieves similar dispatch more simply
- **Abstract Factory** — rarely needed at Python's typical application scale; usually a sign of over-engineering unless building a genuinely pluggable, multi-backend system

### The meta-lesson: patterns are solutions to *recurring problems in a specific language context*
The value of studying patterns isn't memorizing their names/UML diagrams — it's recognizing the **underlying problem shape** (e.g., "I need to decouple an algorithm from the object using it," which is Strategy) and choosing Python's most idiomatic solution to that shape, which may or may not resemble the classical GoF implementation.

## 4. Real-World Example
Python's own `sorted(data, key=some_function)` IS the Strategy pattern, used pervasively throughout the standard library and real codebases — nobody writes a `SortStrategy` class hierarchy in Python; you just pass a function. Recognizing this — that idiomatic Python often already embeds classical patterns invisibly via first-class functions — is a genuine marker of design maturity distinguishing an intermediate from a senior Python engineer.

## 5. Best Practices
- Start with the simplest Python-idiomatic solution (a function, a dict of callables, a dataclass) before reaching for a full class-hierarchy pattern implementation
- Recognize the underlying problem shape a pattern addresses, and evaluate whether Python's dynamic features already solve it more simply
- Reserve heavier patterns (Abstract Factory, Visitor, Builder) for genuinely complex systems where the structure earns its complexity

## 6. Common Mistakes
- Porting verbose, Java-style pattern implementations directly into Python without adapting to the language's features
- Over-applying patterns to simple problems, adding unnecessary abstraction layers
- Missing that a language feature (context managers, decorators, first-class functions) already IS an idiomatic solution to the underlying problem a classical pattern addresses

## 7. Performance Considerations
Over-applied patterns (unnecessary abstraction layers, extra indirection through interfaces/factories) add real function-call and object-creation overhead compared to Python's more direct idiomatic equivalents — simplicity here is both a readability and (modestly) a performance win.

## 8. Security Considerations
Not directly security-relevant, but overly complex, heavily-pattern-laden code is genuinely harder to security-review (more indirection to trace through to understand actual data flow) — simplicity and directness, where appropriate, is a real aid to security auditability.

## 9. Hands-On Exercises
1. Implement the Strategy pattern both the "classical" (class hierarchy) way and the Python-idiomatic (first-class function) way, and compare
2. Implement a Singleton both as a class-based pattern and as a simple module-level instance, and argue for which is more Pythonic
3. Identify 3 places in your Phase 1-3 capstone projects where you unknowingly already implemented a classical pattern idiomatically

## 10. Mini Project
Refactor a piece of code (from an earlier capstone, or provided) that uses an over-engineered classical pattern implementation (e.g., a full Factory class hierarchy for something simple) into idiomatic Python, documenting the simplification and reasoning in a short before/after writeup.

## 11. Interview Questions
- Junior: "What is the Strategy pattern, and how would you implement it in Python?"
- Mid: "Why is a classical Singleton class often unnecessary in Python?"
- Senior: "A junior engineer on your team has implemented a full Abstract Factory hierarchy for a system with only two possible backend types — how do you approach this code review, balancing teaching moment against not being dismissive of design-pattern knowledge?"

## 12. Challenge Exercise
Take a genuinely complex real-world design problem (e.g., a plugin-based data-export system supporting CSV/JSON/XML output with format-specific configuration) and design it from scratch using purely Python-idiomatic tools (Protocols, first-class functions, dataclasses, decorators) — then compare your design against what a "classical GoF pattern" implementation would have looked like, articulating the trade-offs explicitly.
