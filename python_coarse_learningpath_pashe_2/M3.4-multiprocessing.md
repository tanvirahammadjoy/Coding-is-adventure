# Phase 3 · M3.4: Parallelism with `multiprocessing`

## 1. Learning Objectives
- Use `multiprocessing` to achieve real CPU parallelism, bypassing the GIL
- Understand the cost and constraints of inter-process communication (pickling, shared memory)
- Choose correctly between `multiprocessing.Pool` and `concurrent.futures.ProcessPoolExecutor`

## 2. Theory

### Why processes bypass the GIL
Each process has its **own Python interpreter, own memory space, own GIL** — there's no shared mutable state by default, so no GIL contention between processes. This is *why* `multiprocessing` achieves real parallel CPU speedup where `threading` cannot (M3.2/M3.3), at the cost of losing the convenience of shared memory.

### The pickling requirement
Since processes don't share memory, arguments/results must be **serialized** (via `pickle`, by default) to cross process boundaries. This has real implications:
- Arguments and return values must be **picklable** (most objects are; some — open file handles, database connections, lambdas, some locks — are not)
- Serialization/deserialization has real CPU/memory cost — for very fine-grained tasks, this overhead can exceed the parallelism benefit (a real, common mistake: parallelizing too many tiny tasks, where IPC overhead dominates)

### `multiprocessing.Pool` vs `ProcessPoolExecutor`
```python
from concurrent.futures import ProcessPoolExecutor

def cpu_heavy(n): ...

with ProcessPoolExecutor(max_workers=4) as executor:
    results = list(executor.map(cpu_heavy, range(100)))
```
`ProcessPoolExecutor` (from `concurrent.futures`, same module as `ThreadPoolExecutor`) offers a more modern, consistent API than the older `multiprocessing.Pool`, and is generally preferred for new code — both wrap the same underlying `multiprocessing` machinery.

### Shared memory (when you really need it)
`multiprocessing.shared_memory` (3.8+) and `multiprocessing.Value`/`Array` allow genuinely shared memory between processes for specific cases (large NumPy arrays, primitive counters) — avoiding the pickling cost for data that needs to be accessed by many worker processes, at the cost of more complex, manual synchronization (a `Lock` is still needed for safe concurrent mutation).

### WHEN to use multiprocessing vs alternatives
- Genuinely CPU-bound, parallelizable work (image processing, numeric computation not already vectorized) → `multiprocessing`
- I/O-bound work → `threading`/`asyncio` instead (far lower overhead, no pickling cost)
- Already-vectorized NumPy operations → often already using multiple cores internally (via BLAS) or releasing the GIL; adding `multiprocessing` on top may not help and adds real complexity

## 3. Visual Explanation
```
Main process
 ├── spawns → Worker Process 1 [own GIL, own memory]  ← pickled args in, pickled result out
 ├── spawns → Worker Process 2 [own GIL, own memory]
 └── spawns → Worker Process 3 [own GIL, own memory]
  (true parallel execution across cores, but every argument/result crosses via serialization)
```

## 4. Real-World Example
A data pipeline resizing/processing thousands of images sequentially takes hours; parallelizing with `ProcessPoolExecutor` across available CPU cores can cut wall-clock time roughly proportional to core count (e.g., ~4x on a 4-core machine, with some overhead) — a very common, very real production use case, but the team must ensure each task is large enough (per-image processing, not per-pixel) that IPC/pickling overhead doesn't dominate.

## 5. Best Practices
- Batch work into reasonably large chunks per task — avoid parallelizing extremely fine-grained work where IPC overhead dominates
- Prefer `ProcessPoolExecutor` over raw `multiprocessing.Pool` for new code
- Use `shared_memory`/`Value`/`Array` only when profiling shows pickling overhead is a genuine bottleneck for large shared data
- Always guard multiprocessing entry points with `if __name__ == "__main__":` (required on some platforms — Windows/macOS spawn method re-imports the module in each child process)

## 6. Common Mistakes
- Parallelizing tasks too fine-grained, where pickling/IPC overhead exceeds any parallelism benefit
- Forgetting the `if __name__ == "__main__":` guard, causing infinite process spawning or import errors on some platforms
- Trying to share unpicklable objects (open file handles, DB connections) across process boundaries
- Assuming `multiprocessing` will help with I/O-bound work (it adds overhead there with no GIL-related benefit)

## 7. Performance Considerations
The break-even point between multiprocessing's parallelism benefit and its IPC/spawn overhead depends heavily on task size and count — **always benchmark** with real task sizes; a task that takes microseconds is almost never worth parallelizing this way, while a task taking hundreds of milliseconds to seconds usually is.

## 8. Security Considerations
Pickle-based IPC means multiprocessing inherits `pickle`'s security properties — **never** unpickle data from an untrusted source (arbitrary pickle data can execute arbitrary code on load, covered fully in M3.10); this is generally a non-issue for `multiprocessing` used internally (you control both ends), but matters if extending the pattern to any externally-sourced serialized data.

## 9. Hands-On Exercises
1. Parallelize a CPU-bound function (e.g., prime-checking across a range) with `ProcessPoolExecutor` and measure the speedup versus sequential execution
2. Deliberately parallelize a trivially small task (e.g., `x + 1`) across many tiny calls, and observe that overhead makes it SLOWER than sequential — quantify the break-even point
3. Attempt to pass an unpicklable object (e.g., an open file handle) to a worker process and observe/explain the resulting error

## 10. Mini Project
Build an image-processing pipeline (resize/thumbnail a directory of images) that runs sequentially by default, with a `--parallel` flag switching to `ProcessPoolExecutor`, and benchmark/report the speedup at different worker counts (1, 2, 4, 8) to build real intuition for how parallelism scales (and where it plateaus) on your hardware.

## 11. Interview Questions
- Junior: "Why does `multiprocessing` achieve real parallelism where `threading` doesn't, for CPU-bound work?"
- Mid: "What's the cost of using `multiprocessing`, and when could parallelizing actually make code slower?"
- Senior: "Design a batch image-processing service that needs to scale to millions of images/day — walk through your process pool sizing strategy, task granularity decisions, and how you'd monitor for IPC overhead becoming a bottleneck."
