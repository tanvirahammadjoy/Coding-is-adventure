# Phase 2 · M2.7: Iterators, Generators & Lazy Evaluation

## 1. Learning Objectives
- Explain the iterator protocol (`__iter__`/`__next__`) precisely
- Write generator functions using `yield` and understand their execution model
- Know when lazy evaluation (generators) is the right choice vs eager (lists)

## 2. Theory

### The iterator protocol
```python
class CountUp:
    def __init__(self, n): self.n, self.i = n, 0
    def __iter__(self): return self
    def __next__(self):
        if self.i >= self.n: raise StopIteration
        self.i += 1
        return self.i
```
`for x in obj` is sugar for: call `iter(obj)` (invokes `__iter__`), then repeatedly call `next()` on the result (invokes `__next__`) until `StopIteration` is raised. Any object implementing this protocol works with `for`, `list()`, unpacking, etc. — this is the mechanism behind M2.5's "duck typing via `collections.abc.Iterable`."

### Generators — the easy way to build iterators
```python
def count_up(n):
    i = 0
    while i < n:
        i += 1
        yield i
```
A function containing `yield` becomes a **generator function** — calling it doesn't run the body; it returns a generator object implementing the iterator protocol automatically. Execution **pauses** at each `yield`, resuming exactly where it left off (with full local state preserved) on the next `next()` call. This is *why* generators are dramatically simpler to write than a hand-rolled class-based iterator — the state machine is implicit in the function's local variables and instruction pointer, rather than manually tracked in `self`.

### `yield from`
Delegates iteration to a sub-generator/iterable, flattening nested generator composition:
```python
def flatten(nested):
    for item in nested:
        if isinstance(item, list):
            yield from flatten(item)
        else:
            yield item
```

### WHY lazy evaluation matters
A generator produces values **one at a time, on demand**, using constant memory regardless of the logical sequence's size — this is *why* generators can represent (and iterate) infinite sequences, and why they're the correct tool for large/streaming data (direct continuation of M1.8's generator-expression memory lesson, generalized to full generator functions with arbitrary logic).

## 3. Visual Explanation
```
gen = count_up(3)
next(gen)  →  runs until first yield → returns 1, PAUSES (state: i=1)
next(gen)  →  resumes after yield  → returns 2, PAUSES (state: i=2)
next(gen)  →  resumes             → returns 3, PAUSES
next(gen)  →  resumes, loop ends  → raises StopIteration
```

## 4. Real-World Example
Processing a multi-gigabyte log file: `for line in open(path):` already uses this exact lazy mechanism (file objects are iterators yielding one line at a time) — you can build arbitrarily complex processing pipelines (parse → filter → transform) entirely with generators chained together, and the whole pipeline runs in constant memory regardless of file size, a technique used throughout real data-engineering codebases.

## 5. Best Practices
- Use generators for any sequence that could be large or is naturally computed on-demand
- Chain generators for multi-stage pipelines instead of materializing intermediate lists
- Prefer writing a generator function over a hand-rolled iterator class whenever the logic fits a simple function — it's almost always simpler

## 6. Common Mistakes
- Trying to iterate a generator twice (generators are single-use/exhausted after one full pass — unlike lists, which are reusable)
- Accidentally materializing a generator into a list (`list(gen)`) when the whole point was to avoid loading everything into memory
- Forgetting that a generator function's body doesn't execute AT ALL until you start iterating it (a common source of "why didn't my print statement run" confusion)

## 7. Performance Considerations
Generators trade a small per-`next()`-call overhead for **O(1) memory** regardless of sequence length — for large-scale data processing this is usually a decisive win; for small, reusable, or randomly-accessed sequences, a plain list is simpler and sometimes faster (no per-item generator overhead).

## 8. Security Considerations
Generator-based pipelines processing untrusted streaming input (e.g., a large uploaded file) let you enforce limits (max lines processed, timeouts) incrementally as data flows through, rather than being forced to load a whole (potentially malicious, oversized) file into memory first — a legitimate defense against resource-exhaustion attacks.
