# Phase 2 · M2.1: OOP Fundamentals — Classes, Instances & self

## 1. Learning Objectives

- Define classes and instantiate objects correctly
- Explain what `self` actually is and why it must be explicit in Python
- Distinguish class attributes from instance attributes and their shared pitfalls

## 2. Theory

### What a class actually is

A `class` statement creates a **class object** (itself an instance of `type` — previewed here, covered fully in Phase 3's metaclasses module). Calling `MyClass()` invokes `type.__call__`, which allocates a new instance via `__new__`, then initializes it via `__init__`. This two-step process (`__new__` creates, `__init__` configures) is _why_ `__init__` doesn't return anything — the object already exists by the time `__init__` runs.

### Why `self` is explicit

Unlike Java/C++ (where `this` is implicit), Python methods are just functions stored on the class, and `self` is the **first parameter**, explicitly passed. `instance.method(arg)` is syntactic sugar for `ClassName.method(instance, arg)` — this is _why_ `self` must be named explicitly in every method signature, and it directly reflects Python's "explicit is better than implicit" philosophy (M0.1).

### Class attributes vs instance attributes

```python
class Dog:
    species = "Canis familiaris"   # class attribute — shared across ALL instances
    def __init__(self, name):
        self.name = name            # instance attribute — unique per instance
```

Class attributes live on the **class object**; instance attributes live on the **instance's `__dict__`**. Attribute lookup on an instance checks the instance's `__dict__` first, then falls back to the class (and its MRO — Phase 2's M2.2). This is _why_ mutating a **mutable class attribute** (e.g., a class-level `list`) affects all instances — a direct cousin of the mutable-default-argument bug from M1.1.

## 3. Visual Explanation

```bash
Dog (class object)
 ├── species = "Canis familiaris"     (class attribute, shared)
 └── __init__, bark, ...               (methods, shared)

rex = Dog("Rex")          fido = Dog("Fido")
 └── name = "Rex"          └── name = "Fido"     (instance attributes, unique)
 (species looked up via fallback to class)
```

## 4. Real-World Example

A common beginner bug mirroring M1.1's mutable-default-argument trap: defining `class ShoppingCart: items = []` (class attribute) instead of setting `self.items = []` in `__init__` — every `ShoppingCart` instance ends up sharing the _same_ list, so adding an item to one cart mysteriously appears in all carts. This exact bug has appeared in real production e-commerce code.

## 5. Best Practices

- Initialize all mutable instance state inside `__init__`, never as a bare class attribute
- Use class attributes only for genuinely shared, immutable constants/defaults
- Keep `__init__` focused on assigning state, not performing heavy computation or I/O

## 6. Common Mistakes

- Mutable class attributes shared unexpectedly across instances (shown above)
- Forgetting `self` as the first parameter in a method definition
- Doing expensive work (network calls, file I/O) inside `__init__`, making object construction slow/unpredictable and hard to test

## 7. Performance Considerations

Instance attribute access goes through the instance's `__dict__` (a hash table) — for extremely attribute-access-heavy code, `__slots__` (covered in M2.4/M3.1) can reduce memory and speed up access by avoiding a per-instance dict, at the cost of losing dynamic attribute flexibility.

## 8. Security Considerations

Avoid putting sensitive data (API keys, passwords) directly as plain class or instance attributes that might be accidentally logged via a default `__repr__`/`__str__` (covered in M2.3) — this is a common way secrets leak into logs.
