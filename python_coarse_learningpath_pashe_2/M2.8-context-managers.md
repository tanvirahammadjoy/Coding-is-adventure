# Phase 2 · M2.8: Context Managers — `with`, contextlib & Custom Implementations

## 1. Learning Objectives
- Explain the context manager protocol (`__enter__`/`__exit__`) precisely
- Write custom context managers both as classes and via `@contextlib.contextmanager`
- Use `contextlib` utilities (`suppress`, `ExitStack`) appropriately

## 2. Theory

### The protocol
```python
class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self                      # bound to the `as` variable
    def __exit__(self, exc_type, exc_val, exc_tb):
        self.elapsed = time.perf_counter() - self.start
        return False                     # False/None = don't suppress exceptions

with Timer() as t:
    do_work()
print(t.elapsed)
```
`with expr as var:` calls `expr.__enter__()` (binding its return to `var`), runs the block, then **always** calls `expr.__exit__(exc_type, exc_val, exc_tb)` — even if an exception occurred (the three arguments are `None` if not). This is the formal mechanism underlying M1.10's guaranteed `f.close()` behavior, generalized to any resource: locks, database transactions, temporary state changes.

`__exit__` returning `True` **suppresses** the exception (rarely appropriate — most context managers should return `False`/`None` and let exceptions propagate).

### `@contextlib.contextmanager` — the easy way
```python
from contextlib import contextmanager

@contextmanager
def timer():
    start = time.perf_counter()
    try:
        yield start
    finally:
        print(f"elapsed: {time.perf_counter() - start:.4f}s")

with timer():
    do_work()
```
Code before `yield` is `__enter__`; code after (in `finally`) is `__exit__`. This leverages generators (M2.7) to express a context manager far more concisely than a full class — the `try/finally` ensures cleanup runs even if the `with` block raises.

### WHY context managers exist as a first-class concept
Resource cleanup (files, locks, DB connections/transactions, temporary env var changes) needs to run **reliably regardless of how the block exits** (normal completion, `return`, exception, `break`). `try/finally` alone can do this, but context managers make the pattern reusable, composable, and impossible to forget at each call site — a direct, deliberate solution to a recurring class of resource-leak bugs.


## 4. Real-World Example
Database libraries (SQLAlchemy, psycopg) use context managers for transactions: `with session.begin():` ensures a commit on success and a **rollback on any exception** automatically — a critical correctness guarantee (a transaction accidentally left open or half-committed after an unhandled exception is a real, serious production data-integrity bug class this pattern directly prevents).

## 5. Best Practices
- Prefer `@contextmanager` for simple cases; use a class when you need more state or multiple methods
- Always let `__exit__` return `False`/`None` unless deliberately suppressing a specific, well-understood exception type
- Use `contextlib.ExitStack` when managing a *dynamic* number of context managers (not known until runtime)

## 6. Common Mistakes
- Forgetting `try/finally` inside a `@contextmanager` generator, so cleanup doesn't run if the `with` block raises
- Accidentally suppressing exceptions by returning `True` from `__exit__` without meaning to
- Writing manual `try/finally` boilerplate repeatedly instead of extracting a reusable context manager

## 7. Performance Considerations
Context manager overhead is negligible (a couple of method calls) — the real performance consideration is what's *inside* `__enter__`/`__exit__` (e.g., acquiring a lock, opening a connection) — keep that work minimal and fast, especially for context managers used in hot paths.

## 8. Security Considerations
Context managers are the correct pattern for handling locks in concurrent code (preventing deadlocks from a forgotten `.release()`) and for ensuring sensitive temporary resources (e.g., a decrypted temp file) are always cleaned up even on error — relying on manual cleanup for security-sensitive resources is a real risk this pattern directly mitigates.
