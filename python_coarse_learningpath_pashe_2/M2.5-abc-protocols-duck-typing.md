# Phase 2 · M2.5: Abstract Base Classes, Protocols & Duck Typing

## 1. Learning Objectives
- Use `abc.ABC` to define and enforce interfaces
- Use `typing.Protocol` for structural typing (duck typing with static checking)
- Articulate Python's duck-typing philosophy and when to formalize it

## 2. Theory

### Duck typing — the foundational philosophy
"If it walks like a duck and quacks like a duck, it's a duck." Python traditionally doesn't require explicit interface declarations — any object with the right methods/attributes works wherever those methods/attributes are used, checked only at runtime when actually accessed. This is *why* Python historically favored **EAFP** (M1.9) over explicit type-checking — the language's whole design assumes structural compatibility matters more than declared type.

### Abstract Base Classes (`abc`)
```python
from abc import ABC, abstractmethod
class Shape(ABC):
    @abstractmethod
    def area(self) -> float: ...
    @abstractmethod
    def perimeter(self) -> float: ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return 3.14159 * self.r ** 2
    def perimeter(self): return 2 * 3.14159 * self.r
```
`ABC` **enforces at instantiation time** that subclasses implement all abstract methods — `Shape()` directly raises `TypeError`, and so does instantiating a subclass missing `perimeter`. This is *why* ABCs exist: pure duck typing gives no error until the missing method is actually called, potentially deep in production; ABCs fail fast, at construction.

### `typing.Protocol` (PEP 544, structural typing)
```python
from typing import Protocol
class Drawable(Protocol):
    def draw(self) -> None: ...

def render(shape: Drawable) -> None:
    shape.draw()
```
A `Protocol` describes a *shape* (methods/attributes) without requiring explicit inheritance — any class with a matching `draw()` method satisfies it, checked **statically by mypy/pyright**, not at runtime. This is *why* Protocol exists: it formalizes duck typing for static type checkers, giving you IDE/CI-time interface checking WITHOUT forcing every implementer to explicitly inherit from a base class (crucial for typing third-party classes you don't control).

### WHEN to use which
- Pure duck typing: small scripts, quick prototypes, genuinely dynamic use cases
- ABC: you own the class hierarchy and want a hard runtime guarantee that subclasses implement required methods
- Protocol: you want static type-checking of "has these methods," especially across unrelated/third-party classes you can't/won't modify to inherit from a common base

## 3. Visual Explanation
```
Duck typing:    if hasattr(obj, "quack"): obj.quack()          (no formal contract)
ABC:            class Duck(Animal, ABC): @abstractmethod quack  (runtime-enforced contract, requires inheritance)
Protocol:       class Quacks(Protocol): def quack(self): ...    (static-checked contract, no inheritance required)
```

## 4. Real-World Example
The `collections.abc` module's ABCs (`Iterable`, `Sequence`, `Mapping`) are how Python formalizes "things that behave like a list/dict" — implementing `__iter__` and `__next__` makes a class satisfy `Iterable` automatically (ABCs can use `__subclasshook__` for structural checks too), which is *why* your own custom iterable classes work seamlessly with `for x in obj`, `list(obj)`, etc., without inheriting from anything.

## 5. Best Practices
- Use `Protocol` for typing third-party or otherwise-uncontrolled classes structurally
- Use `ABC` when you own the hierarchy and want fail-fast enforcement of a contract
- Don't over-formalize small internal scripts — plain duck typing is fine when the codebase is small and the "contract" is obvious from context

## 6. Common Mistakes
- Using inheritance-based ABCs when you don't control the classes that need to satisfy the interface (Protocol is the right tool there)
- Forgetting that ABC enforcement is runtime-only — mypy won't catch a missing abstract method until you actually try to instantiate
- Over-engineering small scripts with unnecessary interface formalization

## 7. Performance Considerations
ABC/Protocol overhead is purely at class-definition/type-checking time — no runtime performance cost for calling the actual methods once defined; the enforcement mechanism itself is not a hot-path concern.

## 8. Security Considerations
Fail-fast ABC enforcement (catching a missing required method at instantiation, not at first use in production) is itself a reliability/security-adjacent practice — it converts a potential runtime `AttributeError` in a critical path into an immediate, obvious construction-time error caught in testing/CI.

2. Define an equivalent `Shape` as a `Protocol` instead, and demonstrate mypy catching a class missing `area()` without requiring inheritance
3. Explain, with an example, when `collections.abc.Iterable` would recognize a class as iterable without explicit inheritance

## 10. Mini Project
Design a small plugin system: a `Protocol` defining the required interface (`name`, `run(data)`) for plugins, with 3 concrete plugin implementations (none inheriting from a shared base class), and a runner function statically typed against the Protocol — demonstrating structural typing's real value for extensible systems.
