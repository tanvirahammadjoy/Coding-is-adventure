## 2. Theory

### `pyproject.toml` — the modern standard
PEP 518/621 established `pyproject.toml` as the single, standardized configuration file for build systems, replacing the older, more fragmented `setup.py`/`setup.cfg` approach. It declares metadata (name, version, dependencies), the build backend (e.g., `setuptools`, `hatchling`, `poetry-core`), and tool configuration (ruff, mypy, pytest) all in one place — a direct maturation of the ecosystem tying back to M0.3's tooling landscape.

```toml
[project]
name = "expense-tracker"
version = "0.1.0"
dependencies = ["click>=8.0"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"
```

### `src/` layout vs flat layout
```
project/
├── src/
│   └── expense_tracker/
│       ├── __init__.py
│       └── ...
└── tests/
```
The `src/` layout (package code inside `src/`, not at the project root) is now widely recommended over a flat layout — it prevents a subtle but real bug: without `src/`, running tests from the project root can accidentally import the **local uncompiled source** instead of the **actually-installed package**, masking packaging errors that would only surface after a real `pip install`. This ties directly back to M1.11's import-system lessons.

### Building & publishing
```bash
pip install build twine
python -m build              # produces dist/*.whl and dist/*.tar.gz
twine upload --repository testpypi dist/*   # test first!
twine upload dist/*                           # real PyPI
```
A **wheel** (`.whl`) is a pre-built, ready-to-install binary distribution format; a **sdist** (`.tar.gz`) is a source distribution requiring a build step on install. Modern practice publishes both.

### Editable installs for development
`pip install -e .` installs the package in "editable" mode — changes to source code are reflected immediately without reinstalling, essential for local development against your own in-progress package.

### Semantic versioning
`MAJOR.MINOR.PATCH` — increment MAJOR for breaking changes, MINOR for backward-compatible new features, PATCH for backward-compatible bug fixes. This convention lets downstream users set sensible version constraints (`>=1.2,<2.0`) trusting that a MAJOR bump signals "read the changelog before upgrading."

## 4. Real-World Example
A very real, very common bug the `src/` layout prevents: a contributor runs `pytest` from the project root of a flat-layout package, tests pass locally (accidentally importing local source), but the actual published package (built and installed fresh) is broken due to a packaging misconfiguration (e.g., a missing file not included in the built distribution) — undetected until a user reports `ImportError` after `pip install`.

## 5. Best Practices
- Use the `src/` layout for anything intended to be installed/distributed
- Always test against an actual built+installed wheel (not just local source) before publishing
- Follow semantic versioning strictly and maintain a changelog
- Publish to TestPyPI first to verify the process before a real release

## 6. Common Mistakes
- Flat layout masking packaging bugs (tests passing against local source, not the built package)
- Forgetting to include non-`.py` files (data files, templates) in the package manifest
- Publishing a broken version to real PyPI without testing on TestPyPI first (package names/versions can't be reused once published)

## 7. Performance Considerations
Wheel-format distributions install faster than sdists (no build step needed at install time) — publishing pre-built wheels (especially for packages with compiled extensions) meaningfully improves the install experience for downstream users, relevant at CI scale where install time compounds.

## 8. Security Considerations
Never publish secrets/credentials accidentally bundled into a package (a real, recurring incident class — API keys committed into source that gets packaged and published publicly); use PyPI API tokens (not passwords) for publishing, scoped narrowly, and audit `MANIFEST.in`/build output for anything unintended.
