# Phase 2 · M2.6: Functional Programming & Decorators

## 1. Learning Objectives
- Use first-class functions, `map`/`filter`, and `functools` tools idiomatically
- Write your own decorators, including parameterized and stacked ones
- Understand what a decorator actually IS mechanically (a higher-order function)

## 2. Theory

### First-class functions
Functions in Python are objects — assignable to variables, passable as arguments, returnable from other functions. This is the foundation everything in this module builds on.

### `map`/`filter`/`reduce` vs comprehensions
```python
list(map(str.upper, names))                  # functional style
[n.upper() for n in names]                    # comprehension style (M1.8) — usually preferred
from functools import reduce
reduce(lambda acc, x: acc + x, nums, 0)       # rarely idiomatic — sum(nums) is clearer here
```
Python's culture generally **prefers comprehensions over `map`/`filter`** for readability (Guido has spoken publicly against `reduce` specifically, which is why it was moved out of builtins into `functools` in Python 3) — know these tools, but default to comprehensions/built-ins (`sum`, `any`, `all`, `sorted`) where they fit.

### Decorators — what they actually are
A decorator is a function that takes a function and returns a (usually wrapped) function:
```python
def timer(func):
    @functools.wraps(func)        # preserves func's __name__/__doc__ — always use this!
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)
        print(f"{func.__name__} took {time.perf_counter() - start:.4f}s")
        return result
    return wrapper

@timer
def slow_function(): ...
# equivalent to: slow_function = timer(slow_function)
```
`@decorator` is pure syntactic sugar for `func = decorator(func)` — nothing magic, just a higher-order function applied at definition time. This directly builds on M1.7's closures (`wrapper` closes over `func`).

### Parameterized decorators (a decorator factory)
```python
def retry(times=3):
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(times):
                try: return func(*args, **kwargs)
                except Exception:
                    if attempt == times - 1: raise
        return wrapper
    return decorator

@retry(times=5)
def flaky_call(): ...
```
This needs **three** nested levels because `@retry(times=5)` first calls `retry(times=5)` (returning the actual decorator), which is then applied to `flaky_call`.

### Key `functools` tools
- `functools.wraps` — preserves metadata (name, docstring) of the wrapped function; omitting this breaks introspection/debugging tools silently
- `functools.lru_cache` — memoization decorator, built-in, thread-safe
- `functools.partial` — pre-binds some arguments of a function, returning a new callable

## 4. Real-World Example
Web frameworks (Flask, FastAPI) use decorators pervasively for route registration (`@app.get("/users")`), and production code commonly layers decorators for cross-cutting concerns — `@retry`, `@timer`, `@cache`, `@requires_auth` stacked on a single function — each wrapping the previous, executed outermost-first.

## 5. Best Practices
- Always use `@functools.wraps` inside custom decorators
- Prefer `functools.lru_cache` over hand-rolled memoization for simple cases
- Keep decorator stacking order intentional and documented — order matters (outermost decorator wraps everything below it)

## 6. Common Mistakes
- Forgetting `@functools.wraps`, breaking `__name__`/`__doc__` and confusing debuggers/documentation tools
- Writing a decorator that doesn't handle `*args, **kwargs` generically, breaking on any function with a different signature than originally tested
- Misunderstanding decorator stacking order (`@a @b def f()` applies `b` first, then `a` — bottom-up)

## 7. Performance Considerations
Every decorator adds a function-call layer of overhead — usually negligible, but stacking many decorators on an extremely hot-path function is measurable; `functools.lru_cache` specifically trades memory for CPU time and needs a bounded `maxsize` in long-running processes to avoid unbounded memory growth.

## 8. Security Considerations
Auth-related decorators (`@requires_auth`, `@requires_role("admin")`) are a common, legitimate production pattern — but a decorator applied incorrectly (wrong order, or forgotten on a new route) is a real, recurring class of security bug; automated tests verifying protected routes actually reject unauthorized access are essential, not optional.
