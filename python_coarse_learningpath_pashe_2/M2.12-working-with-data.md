## 2. Theory

### CSV — deceptively tricky
`csv.reader`/`csv.DictReader` handle quoting, embedded commas, and escaping correctly — hand-rolling CSV parsing via `.split(",")` breaks the instant a field contains a comma or quote. Always use the `csv` module (or pandas for heavier use), never manual splitting, for anything beyond a guaranteed-trivial format.

### JSON
`json.dumps`/`json.loads` map cleanly to/from Python dicts/lists, with some type gaps to know: Python `tuple` serializes as a JSON array (and deserializes back as a `list`, losing the tuple-ness); `datetime` objects aren't natively JSON-serializable (need a custom encoder or `.isoformat()` conversion); `Decimal` (M1.2) also needs custom handling — a common integration gap between "correct Python types" and "JSON's more limited type system."

### `sqlite3` — embedded SQL, zero setup
Stdlib's `sqlite3` module gives a full relational database in a single file, no server process — excellent for small apps, prototypes, local tools, and even moderate-scale production use cases (SQLite is far more capable than its "toy database" reputation suggests, and is used in real production systems, especially embedded and low-write-concurrency scenarios).

```python
import sqlite3
conn = sqlite3.connect("app.db")
conn.execute("INSERT INTO users (name) VALUES (?)", (name,))   # parameterized — NEVER f-string SQL
conn.commit()
```
**Always use parameterized queries** (`?` placeholders) — string-formatting user input directly into SQL is the textbook SQL injection vulnerability (full treatment in Phase 4's security module, but the habit starts here).

### SQLAlchemy — when raw SQL isn't enough
An ORM (Object-Relational Mapper) maps database rows to Python objects, provides connection pooling, and abstracts across database engines (SQLite → PostgreSQL migration becomes far easier). WHEN to reach for it: multi-table relational apps, when you want Python objects instead of raw tuples/dicts, when you might swap databases later. WHEN NOT to: simple embedded single-table use cases, or when the team needs full control over exact SQL for performance-critical queries (ORMs can generate inefficient queries — the N+1 query problem, covered fully in Phase 4's M4.9).

### A glimpse of NumPy/pandas
Pure Python loops over large numeric datasets are slow (interpreted, per-element overhead). **NumPy** provides fixed-width, contiguous arrays with **vectorized** operations implemented in C — operating on whole arrays at once instead of element-by-element Python loops, often 10-100x faster. **pandas** builds on NumPy for labeled, tabular data (like a DataFrame — think "Excel in Python"). Full depth in Phase 4's M4.7; here, just recognize the signal: "large numeric/tabular data + Python loop" is a strong hint to reach for these libraries instead.

```
Pure Python loop over 1M numbers   →  1M individual Python bytecode operations (slow)
NumPy vectorized operation         →  one call into optimized, compiled C code operating

```

## 4. Real-World Example
A classic real vulnerability: building a SQL query via f-string (`f"SELECT * FROM users WHERE name = '{name}'"`) instead of a parameterized query — trivially exploitable (`name = "'; DROP TABLE users; --"`). This exact pattern is one of the most common and most severe real-world web application vulnerabilities (consistently in OWASP's top risks), and the fix (parameterized queries) costs nothing in complexity.

## 5. Best Practices
- Always use the `csv` module for CSV, never manual string splitting
- Always use parameterized SQL queries, never string formatting/concatenation
- Reach for SQLAlchemy when relational complexity/portability justifies it; stay with raw `sqlite3` for simple embedded cases
- Recognize when numeric/tabular scale signals a need for NumPy/pandas instead of pure Python loops

## 6. Common Mistakes
- Hand-rolled CSV parsing breaking on quoted/comma-containing fields
- SQL injection via string-formatted queries
- Forgetting `conn.commit()` after writes in `sqlite3` (changes silently not persisted)
- Reaching for a full DataFrame/NumPy solution for genuinely tiny datasets where plain Python is simpler and sufficient (over-engineering in the other direction)

## 7. Performance Considerations
NumPy vectorization's speedup over pure Python loops is one of the most dramatic, easily-demonstrated performance differences in the Python ecosystem — recognizing "loop over large numeric array" as a vectorization opportunity is a core professional skill, expanded fully in Phase 4.

## 8. Security Considerations
SQL injection (shown above) and unsafe deserialization (`pickle.loads` on untrusted data — previewed here, covered fully in Phase 3's M3.10) are two of the most consequential, most common real-world Python security vulnerabilities; both are entirely preventable with the correct API usage habits established in this module.
