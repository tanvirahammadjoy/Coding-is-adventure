# Phase 3 · M3.6: Metaprogramming — Metaclasses & Dynamic Class Creation

## 1. Learning Objectives
- Explain what a metaclass is and how `type` relates to every class
- Write a simple custom metaclass and know when (rarely) it's the right tool
- Use `__init_subclass__` as a simpler alternative for many metaclass use cases

## 2. Theory

### "Classes are objects too" — the foundation
In Python, **everything is an object**, including classes themselves. A class is an **instance of a metaclass** — by default, `type`. `type(MyClass)` returns `type` for an ordinary class. This is *why* `class Foo: ...` and `Foo = type("Foo", (), {})` are equivalent — the `class` statement is syntactic sugar for calling the metaclass (`type` by default) with the class's name, bases, and namespace dict.

### Custom metaclasses
```python
class Meta(type):
    def __new__(mcs, name, bases, namespace):
        namespace["created_by"] = "Meta"
        return super().__new__(mcs, name, bases, namespace)

class MyClass(metaclass=Meta):
    pass

MyClass.created_by   # "Meta"
```
A metaclass controls **class creation itself** — it can inspect/modify the class's namespace, enforce conventions across all classes using it, auto-register subclasses, or inject behavior before any instance is ever created. This is a genuinely advanced, rarely-needed tool — used internally by frameworks (Django's ORM `Model` base, ABCs' `ABCMeta`) far more often than in typical application code.

### WHY metaclasses exist despite being rarely used directly
Framework authors need a hook that runs at **class definition time** (not instance creation time) — e.g., Django needs to inspect a model class's declared fields and build database schema information the moment the class is defined, before any instance exists. Metaclasses are the mechanism that makes this kind of "class-level magic" possible.

### `__init_subclass__` — the simpler modern alternative (PEP 487)
```python
class Plugin:
    registry = []
    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        Plugin.registry.append(cls)

class MyPlugin(Plugin): pass   # automatically appended to Plugin.registry — no metaclass needed!
```
For the common case of "run some code whenever a subclass is defined" (e.g., auto-registration, a very common metaclass use case historically), `__init_subclass__` achieves the same result with far less complexity and no metaclass machinery at all — **the modern preferred tool** for this class of problem; reach for a full metaclass only when you need to control something `__init_subclass__` genuinely can't (e.g., modifying the namespace dict before the class body even executes).

### WHEN NOT to use metaclasses
"Metaclasses are deeper magic than 99% of users should ever worry about" is a famous, still-accurate community sentiment (often attributed to Tim Peters). If you're not building a framework, a metaclass is very likely the wrong tool — prefer `__init_subclass__`, class decorators (M3.7), or plain composition first.

## 4. Real-World Example
Django's `ModelBase` metaclass inspects every model class at definition time, extracting declared fields (`CharField`, `IntegerField`, etc.) to build the database schema and query-building machinery — application developers writing Django models never see or think about the metaclass directly, but it's the mechanism making `class MyModel(models.Model): name = models.CharField(...)` "just work" as a full ORM-backed class.

## 5. Best Practices
- Default to `__init_subclass__` for "do something when a subclass is defined" needs
- Reserve actual custom metaclasses for framework-level code with a genuine, specific need
- Document metaclass behavior thoroughly — it's genuinely surprising to readers unfamiliar with the pattern

## 6. Common Mistakes
- Reaching for a metaclass when `__init_subclass__` or a simple class decorator (M3.7) would be far simpler and clearer
- Combining multiple metaclasses via multiple inheritance without understanding metaclass conflict resolution (a genuinely advanced, error-prone corner of the language)
- Writing "clever" metaclass magic that makes a codebase significantly harder for other engineers to understand and debug, without a strong justifying need

## 7. Performance Considerations
Metaclass logic runs once, at class-definition time (import time) — not a per-instance or per-call cost, so metaclasses have no meaningful runtime performance impact on instance creation or method calls beyond whatever they set up.

## 8. Security Considerations
Auto-registration metaclasses/`__init_subclass__` patterns (e.g., a plugin registry) should validate what's being registered if the class definitions could originate from less-trusted code (e.g., dynamically loaded plugins) — blind auto-registration of arbitrary subclasses can be a vector for unexpected code execution if the source of those subclasses isn't fully trusted.
