# Phase 2 · M2.9: Type Hints & Static Typing

## 1. Learning Objectives
- Write accurate type hints using the `typing` module
- Run and interpret mypy/pyright output
- Understand Python's "gradual typing" philosophy and its limits

## 2. Theory

### Gradual typing
Python type hints (PEP 484, added 3.5) are **entirely optional and unenforced at runtime** by default — `def f(x: int) -> str:` does NOT stop you from calling `f("oops")`; the annotation is purely for static analysis tools (mypy, pyright) and documentation/IDE support. This is *why* Python's typing is called "gradual" — you can adopt it incrementally, file by file, mixing typed and untyped code freely, unlike a statically-typed-from-day-one language.

### Core typing constructs
```python
from typing import Optional, Union, TypeVar, Generic, Protocol

def find_user(id: int) -> Optional[User]: ...          # Optional[X] = Union[X, None]
def process(value: int | str) -> None: ...              # modern union syntax (3.10+), preferred over Union[int, str]

T = TypeVar("T")
class Stack(Generic[T]):
    def push(self, item: T) -> None: ...
    def pop(self) -> T: ...
```
**Generics** let a class/function be typed *parametrically* — `Stack[int]` and `Stack[str]` are both valid, type-checked independently, without writing separate classes.

### WHY typing exists despite duck typing (M2.5)
Large codebases (10,000+ lines, many contributors) benefit enormously from catching type mismatches **before** runtime — IDE autocomplete, refactoring safety, and CI-time error catching all improve substantially. This doesn't contradict duck typing philosophically — `Protocol` (M2.5) is exactly the bridge: structural, duck-typing-compatible, but statically checkable.

### Limits — what typing does NOT do
Type hints have **zero runtime effect** by default (no automatic validation) — for runtime validation from type hints, you need a separate library (Pydantic, `dataclasses` + manual checks, `typeguard`). Confusing "type-hinted" with "runtime-validated" is a common and consequential mistake (e.g., trusting an annotated function to reject bad input when it silently won't).

## 4. Real-World Example
Large Python codebases at companies like Dropbox and Instagram adopted mypy at scale specifically to catch a whole class of bugs (wrong argument types, `None`-handling errors) before they reached production, incrementally, file-by-file, over years — a direct real-world validation of gradual typing's core design promise.

## 5. Best Practices
- Type-hint all public function signatures at minimum
- Use `X | None` (3.10+) over `Optional[X]` for new code, but know both
- Run mypy/pyright in CI, not just locally, to make type-checking a hard gate
- Use Pydantic (or similar) when you actually need runtime validation, not just static hints

## 6. Common Mistakes
- Assuming type hints provide runtime validation/enforcement (they don't, by default)
- Overusing `Any` to silence the type checker instead of expressing the actual type
- Inconsistent typing coverage causing false confidence (some functions typed, most not, giving a misleading sense of overall type safety)

## 7. Performance Considerations
Type hints have **zero runtime performance cost** in standard CPython (they're just metadata, mostly unevaluated at runtime for simple cases, though be aware complex hints can add minor import-time cost) — the entire cost/benefit trade-off is about developer time and bug prevention, not runtime speed.

## 8. Security Considerations
Never rely on type hints alone for security-relevant input validation — a function typed `def transfer(amount: Decimal)` will happily accept a malicious/malformed value at runtime if called from untyped or dynamically-constructed code; use a real runtime validation layer (Pydantic) at trust boundaries (API inputs, deserialized data).
