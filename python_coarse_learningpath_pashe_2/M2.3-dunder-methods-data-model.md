# Phase 2 · M2.3: Dunder Methods & the Data Model Protocol

## 1. Learning Objectives
- Implement `__repr__`, `__str__`, `__eq__`, `__hash__`, `__len__` correctly
- Understand why Python's operator behavior is a protocol, not magic
- Know the relationship (and pitfalls) between `__eq__` and `__hash__`

## 2. Theory
Python's "data model" is the set of dunder (`__x__`) methods that let custom objects integrate with built-in syntax — `len(obj)` calls `obj.__len__()`, `obj1 == obj2` calls `obj1.__eq__(obj2)`, `for x in obj` uses `__iter__`. This is the *same mechanism* covered for operators in M1.3 — dunders ARE the mechanism, applied uniformly across the whole language, not a separate special case.

### `__repr__` vs `__str__`
- `__repr__` — unambiguous, developer-facing, ideally something that could recreate the object (`Point(x=1, y=2)`); used by the REPL, debuggers, and as the **fallback** for `__str__` if not defined
- `__str__` — readable, user-facing (`"(1, 2)"`); used by `print()` and `str()`

**Always define `__repr__`** at minimum — debugging without it is painful (default repr is `<Point object at 0x...>`, useless in logs/debuggers).

### `__eq__` and `__hash__` — the critical coupling
If you define `__eq__`, Python automatically sets `__hash__` to `None` (making instances unhashable) **unless you also define `__hash__`**. This is *why* an object considered "equal" by value must have a **consistent hash** — violating this (equal objects with different hashes) breaks dict/set behavior silently and catastrophically (lookups fail unpredictably). The rule: if two objects are `__eq__`-equal, they MUST have the same `__hash__`; the reverse isn't required (hash collisions among unequal objects are fine and expected).

```python
class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __repr__(self): return f"Point(x={self.x}, y={self.y})"
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)
    def __hash__(self):
        return hash((self.x, self.y))   # must be consistent with __eq__
```

## 3. Visual Explanation
```
print(obj)          →  obj.__str__()  (falls back to __repr__ if undefined)
repr(obj)            →  obj.__repr__()
obj1 == obj2          →  obj1.__eq__(obj2)
{obj1, obj2}          →  requires obj.__hash__() (and __eq__ for dedup logic)
len(obj)              →  obj.__len__()
```

## 4. Real-World Example
A real production bug class: defining `__eq__` on a class used as dict keys or set members, without defining `__hash__` — the class silently becomes unhashable (`TypeError: unhashable type`) the moment someone tries to put it in a set, often discovered late, in an unrelated part of the codebase far from where `__eq__` was added.

## 5. Best Practices
- Always define `__repr__` for any class beyond the most trivial
- If you define `__eq__` and need instances to be hashable, always define a consistent `__hash__` alongside it
- Base `__hash__` on the same fields used in `__eq__`, as an immutable tuple
- Consider `dataclasses` (`@dataclass`) to auto-generate `__init__`, `__repr__`, `__eq__` correctly (previewed here, standard tool by Phase 2's end)

## 6. Common Mistakes
- Defining `__eq__` without `__hash__`, silently breaking hashability
- Basing `__hash__` on mutable fields (hashing a mutable object, or mutating fields used in an existing hash after insertion into a set/dict — corrupts the container's internal structure)
- Never defining `__repr__`, leaving debug output as useless default `<ClassName object at 0x...>`

## 7. Performance Considerations
`__eq__`/`__hash__` are called potentially very frequently for objects used heavily in sets/dicts — keep them cheap (avoid expensive computation inside `__hash__` on every call); consider caching a precomputed hash for immutable objects.

## 8. Security Considerations
A poorly implemented `__eq__` that doesn't properly type-check `other` (e.g., no `isinstance` check) can raise unexpected exceptions or produce incorrect equality results when compared against untrusted/unexpected types — always guard `__eq__` with an `isinstance` or `NotImplemented` return for mismatched types.
