# Phase 3 · M3.11: Advanced Regex & Text Parsing

## 2. Theory

### Regex fundamentals recap and advanced features
Beyond basic matching (M2.11): named groups (`(?P<year>\d{4})`), lookahead/lookbehind (`(?=...)`, `(?<=...)`) for matching without consuming, non-greedy quantifiers (`.*?` vs `.*`), and the `re.VERBOSE` flag for writing readable, commented multi-line patterns instead of dense single-line regex.

### Catastrophic backtracking (ReDoS)
```python
import re
re.match(r"(a+)+b", "a" * 30 + "!")   # can hang for a VERY long time
```
Certain regex patterns (nested quantifiers, ambiguous repetition) cause the regex engine to try an **exponential number of matching paths** when the input doesn't match — this is *why* ReDoS is a genuine denial-of-service vector: an attacker crafting a specific input string against a vulnerable pattern can hang a process for seconds, minutes, or effectively forever, with a tiny, cheap-to-send payload.

### WHY regex has this failure mode
Python's `re` module uses a **backtracking** engine (like most mainstream regex implementations — Perl, Java, JavaScript) rather than a finite-automaton-based engine (like Google's `re2`, which guarantees linear-time matching but supports a more restricted feature set). Backtracking engines support more expressive patterns (backreferences, lookaround) at the cost of potentially exponential worst-case time on pathological patterns.

### Mitigations
- Avoid nested quantifiers over the same character class (`(a+)+`, `(a*)*`)
- Use `re2` (a third-party binding to Google's linear-time engine) for regex matching against genuinely untrusted input, when the feature set allows it
- Set a timeout on regex matching against untrusted input where possible (some libraries support this; stdlib `re` historically doesn't have a built-in timeout, a real, known limitation)
- Validate/bound input length before applying regex to untrusted data

### WHEN regex is the wrong tool: use a real parser
Regex can match **regular languages** — it fundamentally cannot correctly parse **recursively nested structures** (balanced parentheses, JSON, HTML/XML, programming language syntax) — attempting to do so with regex produces fragile, incorrect edge-case handling (the famous "you can't parse HTML with regex" community meme reflects a genuine formal-language-theory limitation, not just a stylistic preference). For these, use a real parser: the `json` module, an XML/HTML parser library, or — for genuinely custom formats — hand-written tokenizer + recursive-descent parser (previewed conceptually in M1.4's expression-evaluator challenge, and covered more fully in Phase 4's compiler-adjacent content).

## 4. Real-World Example
ReDoS vulnerabilities have caused real, documented production outages — a validation regex on a user-submitted field (e.g., email or URL validation) with a subtly nested-quantifier pattern, deployed for months without issue, then hung the entire request-handling process when a user (accidentally or maliciously) submitted a specific pathological string, taking down the service until the process was killed and the pattern fixed.

## 5. Best Practices
- Avoid nested quantifiers over overlapping character classes in any regex applied to untrusted input
- Test regex patterns against pathological/adversarial inputs, not just expected valid/invalid examples
- Use a real parser (not regex) for any recursively-nested format
- Use `re.VERBOSE` and named groups for any regex complex enough to need comments

## 6. Common Mistakes
- Writing ReDoS-vulnerable patterns without realizing it (this is genuinely subtle — even experienced engineers write vulnerable patterns unintentionally)
- Attempting to parse HTML/XML/JSON/nested structures with regex instead of a proper parser
- Overly dense, uncommented regex that becomes unmaintainable and hard to verify for correctness or security

## 7. Performance Considerations
Regex matching against untrusted input without ReDoS awareness is a genuine, exploitable performance/availability risk (this module's core lesson) — for regex applied to trusted, bounded, well-understood input, standard `re` performance is fine and rarely a bottleneck.

## 8. Security Considerations
This entire module centers on a real security concern (ReDoS) — treat any regex pattern applied to untrusted/user-controlled input with the same scrutiny as SQL query construction (M2.12) or pickle usage (M3.10): a specific, well-known vulnerability class with well-known mitigations that should be applied systematically, not left to chance.
