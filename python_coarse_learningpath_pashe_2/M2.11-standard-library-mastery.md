# Phase 2 · M2.11: Standard Library Mastery

## 1. Learning Objectives
- Use `collections`, `itertools`, `datetime`, `json`, `re`, `logging`, `argparse` fluently
- Know when a stdlib tool exists specifically to replace a naive hand-rolled pattern
- Configure `logging` correctly for a real application (not just `print`)

## 2. Theory

### `collections` — specialized container types
- `defaultdict(list)` — dict with an automatic default factory for missing keys, eliminating manual `if key not in d: d[key] = []` boilerplate
- `Counter` — a dict subclass for counting hashable items (`Counter(words).most_common(5)`)
- `deque` — a double-ended queue with **O(1)** append/pop from *both* ends (unlike `list`, which is O(n) at the front — direct callback to M1.6's Big-O table)
- `namedtuple` — lightweight, immutable, attribute-accessible tuples (largely superseded by `dataclasses`/`typing.NamedTuple` for new code, but still common in legacy code and some stdlib APIs)

### `itertools` — efficient, composable iteration
`chain`, `islice`, `groupby`, `combinations`, `permutations`, `count`, `cycle` — building blocks for constructing complex lazy pipelines (M2.7) without writing manual loops; deeply idiomatic in data-processing code.

### `datetime` — dates, times, timezones
The classic trap: **naive vs aware** datetimes. A naive `datetime` has no timezone information — comparing/arithmetic between naive and aware datetimes raises errors, and naive datetimes are a notorious source of subtle production bugs (server timezone assumptions, DST issues). Modern best practice: **always use timezone-aware datetimes** (`datetime.now(timezone.utc)`), store/compute in UTC, convert to local time only for display.

### `logging` — the correct alternative to `print`
```python
import logging
logger = logging.getLogger(__name__)
logger.info("processing order %s", order_id)   # lazy formatting (M1.5) — NOT an f-string here
```
`logging` supports levels (DEBUG/INFO/WARNING/ERROR/CRITICAL), structured configuration (handlers, formatters routing to files/stdout/remote systems), and per-module control — none of which `print` provides. Production code should never use bare `print` for anything beyond a genuinely temporary debugging aid.

### `re` — regular expressions
Powerful but easy to misuse for tasks better solved by simple string methods (`.split()`, `.startswith()`) — reserve regex for genuinely pattern-based matching, and always compile (`re.compile`) patterns reused across many calls for efficiency.

### `argparse` — CLI argument parsing
Stdlib's structured way to build command-line interfaces with typed arguments, help text, and subcommands — the foundation the Phase 1 capstone's CLI should be built on (or a third-party alternative like `click`/`typer`, previewed in Phase 4's M4.10).

## 3. Visual Explanation
```
Naive pattern                          →  stdlib replacement
if k not in d: d[k] = []; d[k].append(x)  →  defaultdict(list)[k].append(x)
counting occurrences by hand              →  Counter(items)
list used as a queue (O(n) pop(0))        →  deque (O(1) popleft())
manual "for i, (a,b) in enumerate(zip(...))"  →  itertools tools where appropriate
```

## 4. Real-World Example
A very common real bug: using a plain `list` as a task queue with `.pop(0)` for dequeuing — O(n) per operation, silently turning an intended O(n) total-processing algorithm into O(n²) as the queue grows; swapping in `collections.deque` (O(1) `popleft()`) is a one-line fix with dramatic real-world performance impact at scale, directly extending M1.6's Big-O lessons.

## 5. Best Practices
- Reach for `collections`/`itertools` tools before hand-rolling equivalent logic
- Use `logging`, never bare `print`, in any code beyond a quick throwaway script
- Always use timezone-aware datetimes; store/compute in UTC
- Compile regex patterns used repeatedly with `re.compile`

## 6. Common Mistakes
- Using `list.pop(0)` for queue-like behavior instead of `deque`
- Naive datetime handling causing timezone bugs
- Using `print` debugging left in production code, with no way to control verbosity or route output
- Regex misuse for simple string tasks better solved by `.split()`/`.startswith()`/`.endswith()`

## 7. Performance Considerations
`deque` vs `list` for queue operations is a textbook real-world Big-O win (O(1) vs O(n) per dequeue); `Counter`/`defaultdict` eliminate redundant dict lookups compared to hand-rolled equivalents; compiled regex avoids re-parsing the pattern on every call in a loop.

## 8. Security Considerations
Poorly constructed regex patterns (especially with nested quantifiers) can be vulnerable to **ReDoS (Regular Expression Denial of Service)** — catastrophic backtracking on crafted input can hang a process; validate/limit regex complexity when matching against untrusted input, and consider a regex-complexity-bounded library for adversarial input.
